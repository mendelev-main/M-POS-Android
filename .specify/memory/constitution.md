# M POS Android Constitution

## Core Principles

### I. Локальная касса работает независимо от интернета
Продажи, чеки, смены, товары, рецептуры, остатки, закупки, приёмка, инвентаризация и локальная печать не должны зависеть от доступности backend.
Критические локальные данные сохраняются до любой сетевой операции. Сбой сети не может блокировать обычную работу кассы.

### II. Совместимость данных важнее рефакторинга
Существующие `prilavok_` ключи, JSON-структуры и backup schema v13 сохраняются совместимыми с production iPad POS до отдельной согласованной миграции.
Изменение формата данных требует явной миграции, обратной совместимости там, где она нужна, и теста восстановления старых данных.

### III. Android-оболочка и web runtime имеют чёткие границы
Текущий проверенный HTML/JavaScript runtime остаётся источником существующей бизнес-логики до контролируемой миграции.
Kotlin используется для Android-специфичных границ: lifecycle, LAN ESC/POS, фото, файлы, backup, системный share, отчёты и другие platform APIs.
Нативизация выполняется по одному завершённому модулю за раз; массовое переписывание работающей бизнес-логики без отдельной спеки запрещено.

### IV. Offline-first и направление синхронизации сохраняются
Основное направление данных: POS → Backend → Web / Mini App.
Полная синхронизация каталога остаётся ручной. Автоматический импорт каталога или автоматическая перезапись локальных данных backend-ом не добавляются без нового явного решения.
Availability и другие сетевые публикации не должны становиться условием локальной оплаты.

### V. Производственная идентичность Android-приложения стабильна
Package ID `com.mendelev.mpos` после первой production-установки не меняется без отдельного плана миграции.
Production APK подписываются одним постоянным release signing key. Keystore, пароли, токены, production backup и реальные данные не коммитятся в Git.
Каждая production-версия увеличивает `versionCode`; обновление поверх установленного APK не должно требовать удаления приложения или потери локальных данных.

### VI. M POS — единственный naming для нового кода
Все новые и переписываемые Android/Kotlin/Compose/runtime модули используют naming `M POS` / `MPos`. Название `Prilavok` не используется в новых классах, API, namespaces, документации или UI. Старые `PrilavokCore` и `prilavok_` допускаются только как явно помеченная compatibility boundary для ещё не мигрированного shared runtime, backup schema v13 и существующих данных. Compatibility alias удаляется вместе с соответствующим legacy-модулем после принятой миграции.

### VII. Доказательства важнее статуса «готово»
Автоматические тесты, Android lint, debug/release build и физическая проверка на планшете являются разными уровнями доказательств.
Критические сценарии — продажа, split payment, возврат, смена, восстановление backup, LAN-печать, WEB-заказы и восстановление после перезапуска — считаются принятыми только после соответствующей проверки.
Поддержка разных производителей, размеров экранов, разрешений и плотностей должна сохраняться; модель-специфичные зависимости не добавляются без необходимости.

## Product Constraints

M POS Android поддерживает Android 9+ (minSdk 28) и использует package `com.mendelev.mpos`.
POS UI поставляется внутри APK и не загружается из сети.
Нативная LAN ESC/POS-печать является основной аппаратной интеграцией; новые способы печати добавляются отдельной спецификацией.
Production iPad POS остаётся контрольной реализацией для parity-функций до формального принятия Android-версии.

## Spec-Driven Workflow

Постоянные правила находятся в этой конституции и `AGENTS.md`.
Каждая существенная новая функция или миграция ведётся в отдельном `specs/NNN-short-name/` и должна иметь как минимум `spec.md`, `plan.md` и `tasks.md`.
Существующая `specs/001-android-parity/` сохраняется как первая feature-spec и история переноса.
Для крупных нативных миграций должны быть описаны граница между JS и Kotlin, стратегия данных, rollback/совместимость и физические acceptance cases.

Перед изменением проверяется существующая реализация и связанные спецификации.
После изменения выполняются релевантные автоматические проверки; физические проверки фиксируются отдельно и не подменяются фактом успешной компиляции.

## Governance

Явные новые решения пользователя имеют приоритет над прежними проектными предположениями и должны отражаться в спецификациях или поправке конституции.
Изменение принципа — major, добавление принципа — minor, уточнение формулировки — patch.
Секреты и signing material никогда не добавляются в репозиторий.
