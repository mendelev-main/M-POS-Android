# M-POS: инструкции агенту

## Контекст

Нативный Kotlin/Compose POS с локальным хранением. Продуктовые требования — `GOALS.md`, порядок — `PLANS.md`. Выбранный стек и границы подключения зависимостей — `docs/STACK.md`; целевые библиотеки не считать уже установленными. Источник поведения: срез Web в `docs/SOURCE.md`, а не HEAD другого проекта. В этом репозитории новый код с нуля; правила чужого `AGENTS.md` не применяются автоматически.

## Рабочий цикл

- Основная рабочая ветка — `develop`; правила CI/выпуска — `docs/DEVELOPMENT-WORKFLOW.md`. Инкременты не вливать в `main` и не публиковать по отдельности. Готовый блок идёт PR `develop → main`; merge запускает полный выпуск.

- Перед предметной работой прочитайте `harness/build/<этап>.md`, его зависимости, `docs/PARITY.md` и относящиеся к задаче документы. Для этапной работы используйте `$mpos-phase` из `.agents/skills/`.
- Выполняйте текущую задачу в рамках этапа; не начинайте следующие этапы только потому, что предыдущий закончен. Маленькие необходимые исправления инфраструктуры допустимы.
- Фиксируйте значимые решения и незакрытые вопросы в `harness/context/`; результаты команд и ограничения — в `harness/build-log.md`. План и наличие кода не являются доказательством прохождения теста.
- Для бизнес-логики используйте `$mpos-domain`, для выпуска — `$mpos-release`. Не загружайте все исходники и документы заранее.
- Обновляйте parity по конкретным acceptance IDs. Состояния: planned / implemented / ci-verified / device-verified. Не ставьте verified без наблюдаемого результата и ссылки/команды.

## Инварианты

- Целевая платформа Android16+/API36+: minSdk36 и обязательный CI emulator36. Старые runs28/35 — история, не действующая матрица; docs/ANDROID-SUPPORT.md.

- Kotlin — единственный владелец бизнес-логики. Compose отображает состояние и отправляет действия; никаких WebView/JS бизнес-runtime.
- Сначала локальная транзакция, затем UI успеха и внешние эффекты. Отказ записи не должен выглядеть успешной продажей. Сеть не требуется для локальной кассы.
- Расчёты денег и количеств — по `docs/DATA.md`; не использовать Double для денежных сумм и не округлять склад до 0.001.
- Отмена/возврат используют исторический снимок, не текущую рецептуру. Проверки ролей ставить в use case, не только на кнопке.
- Production applicationId `com.mendelev.mpos` и закреплённый сертификат неизменны после первого выпуска. Web — `com.mendelev.mpos.web`. Providers использовать `${applicationId}`.
- Не коммитить ключи, пароли, реальные backup/клиентские данные. Не запускать реальные оплаты, отправку Telegram, печать или production sync ради теста; использовать fake adapters.

## Единый UI

Дизайн — из pinned Web, обязательный контракт `docs/DESIGN-SYSTEM.md` и `config/ui-design.json` (пока specification-only). Использовать shared Mpos theme/components в M01: Close/Back/Primary/Secondary/Danger/Dialog/Field. Не вводить локальные радиусы, крестики и стили кнопок для каждого feature без documented variant. Stock редактируется в карточке без обязательной причины; ledger/revision остаются обязательными (ADR-005).

## Проверки

`python3 scripts/harness.py preflight` — структура, ссылки, skills, идентичность и границы native.
`python3 -m unittest discover -s scripts/tests -v` — инструменты выпуска/harness.
`python3 scripts/harness.py android` — `testDebugUnitTest lintDebug assembleDebug`.
`./gradlew connectedDebugAndroidTest` — UI smoke, требует устройство/emulator.
`git diff --check` — перед завершением изменений.

Используйте wrapper и закреплённые версии; не подавляйте ошибки CI, не снижайте gates для зелёного статуса. Если SDK/сеть отсутствуют, записать точный blocker; не заявлять прохождение Android проверки. Новые сценарии денег/склада/миграций требуют поведенческих тестов, включая сбой записи и повтор команды. Не добавлять тесты, которые только проверяют текст своей реализации.

Документация и общение по умолчанию по-русски; Kotlin identifiers и технические API — по-английски. Не требуется отдельное разрешение на обычные исправления в уже поставленной задаче.
