# Статус миграции M POS Android и проверки на планшете

Срез: 6 октября 2026 года, после спецификаций 040–053. Пользователь разрешил нативные переключения сразу после автоматических проверок; комплексная ручная приёмка перенесена на конец миграции. Основание: дорожная карта, матрица совместимости, спецификации 002–039 и текущая реализация. «Реализовано» означает наличие кода; «принято» требует результатов физических проверок.

Для доли кода учитываются 72 production Kotlin-файлов в app/src/main/java, 43 JS-файлов в app/src/main/assets/pos и встроенный исполняемый JavaScript в pos.html. Не учитываются тесты, документация, HTML-разметка, CSS, ресурсы, Gradle и сгенерированный код. Используются байты UTF-8, чтобы разное форматирование и короткие JS-строки не превращались в искусственный процент по количеству строк. Комментарии остаются в объёме соответствующих исходников.

30,04% — **доля языка, не оценка завершённости миграции по сложности, ценности или трудозатратам**. Точный общий процент выполнения нельзя вывести без согласованной декомпозиции и весов задач. Основное хранение уже переключено для девяти документов: products, layout, posNavigation, employees, shifts, orders, parked, currentOrderSession и criticalStorageJournal; это не перенос финансовых движков или Compose-экранов. Многие Kotlin-платформенные функции существовали до последних этапов; они включены в текущий срез, а не приписаны последним изменениям.

Сотрудники и права доступа пока также обслуживаются существующим runtime: P2 уже перенёс хранение сотрудников в Kotlin, но не переносит авторизацию автоматически. Для экранов зала/столов/бронирований нужна отдельная детализация после стабилизации данных; готовой нативной реализации и утверждённой отдельной спецификации для них сейчас нет. Это оставшиеся части существующего приложения, а не молча завершённые этапы.

Не планируем переписывать всё сразу, заменять рабочий нативный ESC/POS, добавлять другой cross-platform runtime, автоматическую синхронизацию каталога или менять v13 без отдельной миграции.

Политика остатков после ошибки реализована Android JS-адаптером (033), **не переносом на Kotlin**: повтор только после следующей сохранённой оплаты. Фотографический отчёт смены (034) — Kotlin-представление, **не нативный финансовый движок смены**. Последние 035–039 укрепляют уже начатые нативные границы.

## Что проверить сейчас — обычные действия на планшете

Тестировать на отдельной тестовой установке с синтетическими данными. Для каждой проверки записать результат. Не восстанавливать тестовую копию поверх рабочей кассы. Для этого среза нужен APK с изменениями 040–053: старые APK до этих спецификаций ещё использовали каталог/раскладку как сравнительные копии. В GitHub Actions артефакт называется M-POS-Android-debug; workflow теперь запускает JVM-тесты и обе сборки; наличие успешной загрузки конкретного артефакта нужно проверить в выбранном запуске. Локально обе APK-сборки созданы, release APK пока без производственной подписи.

## Технические проверки — могу выполнять с вами

Эти пункты нельзя считать выполненными только по работе UI. Нативные сравнения не имеют отдельного пользовательского экрана.

- [ ] На debug APK подключить Chrome remote debugging (`chrome://inspect`) по USB и вызвать `await MPosCore.CatalogCutover.health()` в консоли WebView. Ожидается `comparison.ok:true`, `comparison.matches:true`, одинаковые количества товаров/категорий, `activeSource:'room'`, `roomCutoverAllowed:true`. Проверить после изменений, перезапуска и восстановления копии. Это необходимые, но не достаточные условия переключения: поля и порядок также сверяются с тестовыми данными.
- [ ] Проверить совпадение нативной копии настроек с UI. В консоли отправить `window.webkit.messageHandlers.settings.postMessage({action:'getPlatformSettings',requestId:'tablet-settings-check'})`; ответ приходит асинхронно в `window.__lastNativeSettingsResult`. После его получения сверить `snapshot.settings`; отсутствие немедленного ответа не означает ошибку.
- [ ] Явно включить диагностический SSE и сравнить один известный тестовый поток с браузером: Unicode, пробелы, несколько data-строк, пустые сообщения, именованные события. Затем обрыв связи и фон/возврат. Результаты last-hash сравнения сами по себе не доказывают совпадение всех событий двух асинхронных соединений.
- [ ] На тестовой установке проверить большой каталог/историю, нехватку места и остановку во время нативной записи. Данные JS должны оставаться пригодными; устаревший Room-снимок не должен выдавать успешное сравнение. Если условия отказа не создавались — записать «не проверено».
- [ ] Ограничения: полный файл больше 500 000 000 байт отклоняется, декодированное фото больше 2 000 000 байт отклоняется. Огромные тестовые файлы необязательны для обычной проверки на планшете; граничное чтение покрыто автоматическими тестами. Допустимый по размеру файл не гарантирует достаточную память на любом устройстве.

## Как прислать результаты

Для каждого пункта: номер/название, «прошло / ошибка / не проверено», ожидание и фактическое поведение. Указать модель планшета, Android, commit APK, ширину/модель принтера для печати. Пример: «Перезапуск после изменения товара — прошло, цена и порядок сохранились». Для ошибки описать шаги воспроизведения; не присылать секреты или рабочие резервные копии.

Последняя автоматическая проверка приложения: 150 JavaScript- и 161 JVM/Kotlin-тестов прошли, lint 0 ошибок/15 предупреждений, debug и minified unsigned release собраны. Эти результаты не заменяют приведённые физические проверки. Нативное хранение и частичная команда оплаты описаны в спецификациях 040–053; расчёт кассы нативной оплаты теперь Kotlin, остальные финансовые границы ещё частично JS.

## Дополнение 042–043 — сотрудники и смены

Основное хранение employees и shifts теперь Kotlin/Room. Полный JSON и исходные роли, поля сотрудника, финансовые значения и кассовые движения сохранены. Документ и индексы записываются атомарно; после переключения устаревшая legacy-копия не заменяет Room. Проверки доступа и финансовые расчёты остаются в JS — этот этап не заявляет перенос их движков.

Для итоговой ручной проверки:

- [ ] Создать и изменить сотрудников разных ролей, проверить вход и разрешённые/запрещённые действия после перезапуска.

## Дополнение 047 — отдельные записи чеков и страницы истории

Основное хранение корректных архивов orders теперь — полные записи отдельных чеков в Room. Snapshot-запись меняет только изменившиеся/удалённые чеки и связанные позиции/оплаты; повтор неизменённого снимка не переписывает архив. Native API поддерживает отдельный upsert с проверкой ревизии. История читает SQL-страницы по 50 чеков; доступно больше 300 записей. Старые некорректные ID сохраняются в совместимом полном документе.

Вторичная legacy-копия архива теперь инвалидируется; бэкап v13 собирается из актуального native состояния. Откат требует свежего полного экспорта/копии. JS-платежи и возвраты ещё передают полный массив, журнал хранит полный снимок и расчёты/startup загружают весь архив; это оставшиеся расходы следующего этапа бизнес-команд.

Итоговые проверки: архив 325+ чеков, одинаковые даты, переключение страниц, новая оплата/возврат с открытой историей, выбор/печать/возврат чека на разных страницах, принудительный перезапуск и v13 round-trip. Проверить старый нестандартный архив без потери записей.

## Дополнение 048 — нативная команда завершения оплаты

Одна Room-транзакция теперь проверяет платёжные части и актуальность исходных данных, списывает исторический stockConsumption, проверяет кассу доставки, сохраняет смену, один чек и очищает корзину. В запросе/платёжном журнале больше нет полного архива заказов. Повтор идентичной команды после потери подтверждения/перезапуска не создаёт второй чек или списание; повтор с иными данными того же ID отклоняется. Новые внешние действия не добавлены.

P7 частично нативный. Расчёт цены, скидок/подарков и раскрытие рецепта остаются JS; другие критические операции ещё используют журнал. Физическая приёмка по-прежнему в конце: наличные, карта, split, доставка, подарки/нулевая сумма, дробные ингредиенты, прерванная запись, перезапуск и v13.

Бизнес-кейс для отдельного исправления: в новой смене было 100 наличными; возврат 20 за чек прошлой смены оставляет расчётный остаток 100 вместо физических 80. Воспроизведено на существующем shifts.js; формула кассы компенсирует все refund-движения. Исправлено отдельной спецификацией 049 по запросу пользователя: продажа остаётся в исходной смене, возврат относится к смене выполнения.

## Дополнение 049 — касса и межсменные возвраты

Кейс 100 ₽ → возврат старого чека 20 ₽ теперь даёт 80 ₽. Закрытая смена сохраняет исходную продажу. Возвраты относятся к returnedShiftId; старые чеки без этого поля используют исходную смену. Исправлены расчёты текущего экрана/истории/отчётных данных и нативная проверка наличных для доставки. P8 частично перенесён; сама команда возврата и открытие/закрытие смен ещё не перенесены. Эта граница реализована спецификацией 050 для чеков с историей списания.

## Дополнение 050 — полный возврат в Kotlin

Возврат современных чеков теперь сохраняет исторические остатки, один чек и движение наличных одной транзакцией Room, без полного архива в запросе/журнале. Повтор после потери подтверждения не удваивает остатки/движение. Импорт копии до возврата допускает новую операцию с новым временем, а старый повтор не подтверждает восстановленный чек.

Бизнес-ограничение для обсуждения позже: старые чеки без stockConsumption восстанавливаются по текущему рецепту; после его изменения точный исторический состав неизвестен. Сохраняем прежний путь без выдумывания состава. Возврат по карте по-прежнему выполняется отдельно через терминал. Команды внесения/изъятия реализованы спецификацией 051.

## Дополнение 051 — внесение и изъятие наличных

Kotlin проверяет актуальность смены, наличные с учётом межсменных возвратов и сохраняет одно ручное движение с маркером одной транзакцией. Ошибка не оставляет частично записанного движения, повтор после потери ответа не удваивает сумму. Копии v13 и комментарии сохранены. Открытие/закрытие смен и экран ещё JS.

Для последующего бизнес-решения: отрицательная расчётная касса сейчас блокирует даже внесение; handler принимает сумму 0,001 без округления до двух знаков. Эти правила сохранены. Жизненный цикл реализован спецификацией 052.

## Дополнение 052 — открытие/закрытие смены

Kotlin проверяет актуальность сотрудника/смены, переносит пересчитанные наличные последней закрытой смены и сохраняет открытие/закрытие одной транзакцией с маркером. Закрытие сверяет кассу и число чеков; фактическая сумма может отличаться в обе стороны. Запись не очищает неоплаченную корзину или отложенные заказы — это существующее поведение.

Пароль администратора проверяется прежним UI; новых копий константы или механизмов авторизации не добавлено. Telegram/месячный отчёт/печать запускаются после сохранения. PNG-формат сохранён. Данные отчёта и экран ещё JS; модель итогов/отчёта реализована в 053; следующая граница — нативный экран смены.

## Дополнение 053 — данные отчёта смены в Kotlin

Итоги и совместимый отчёт строятся из одного снимка Room. Telegram PNG, LAN-чек, PDF и окно отчёта используют эту модель; устаревшие финансовые значения WebView игнорируются. Параллельные автоматические выходы разделяют одно чтение, но получают независимые копии; ручные повторные запросы читают свежие данные. Ошибка чтения не отменяет закрытие и не отправляет старый отчёт.

Сохранены порядок/состав чеков, комментарии, настройки принтеров и правило iPad по числу всех чеков в изображении. Начальный/основной экран смен ещё JS-зеркало, пароль администратора прежний. Чтение не меняет данные и бэкап v13; физические проверки изображений/принтеров/большого архива в конце.
