Сотрудники и права доступа пока также обслуживаются существующим runtime: P2 уже перенёс хранение сотрудников в Kotlin, но не переносит авторизацию автоматически. Для экранов зала/столов/бронирований нужна отдельная детализация после стабилизации данных; готовой нативной реализации и утверждённой отдельной спецификации для них сейчас нет. Это оставшиеся части существующего приложения, а не молча завершённые этапы.

Не планируем переписывать всё сразу, заменять рабочий нативный ESC/POS, добавлять другой cross-platform runtime, автоматическую синхронизацию каталога или менять v13 без отдельной миграции.

Политика остатков после ошибки реализована Android JS-адаптером (033), **не переносом на Kotlin**: повтор только после следующей сохранённой оплаты. Фотографический отчёт смены (034) — Kotlin-представление, **не нативный финансовый движок смены**. Последние 035–039 укрепляют уже начатые нативные границы.

## Что проверить сейчас — обычные действия на планшете

Тестировать на отдельной тестовой установке с синтетическими данными. Для каждой проверки записать результат. Не восстанавливать тестовую копию поверх рабочей кассы. Для этого среза нужен APK с изменениями 040–053: старые APK до этих спецификаций ещё использовали каталог/раскладку как сравнительные копии. Ранее Actions публиковал M-POS-Android-debug; новый CI публикует M-POS-Android-release-<version> после подключения постоянного ключа и успешной проверки. Наличие артефакта проверяется в конкретном запуске. По текущему правилу APK локально не собираем; артефакт создаёт GitHub Actions после коммита.

- [ ] Добавить/изменить/удалить товар и категорию. Закрыть приложение, принудительно остановить через настройки Android и открыть снова. Все сохранённые поля и порядок должны сохраниться.
- [ ] Сохранить v13-копию, восстановить в чистую тестовую установку и перезапустить. Сравнить товары, фото, рецепты, сотрудников, смены, чеки и отложенные заказы. Проверить iPad → Android при наличии iPad.
- [ ] Открыть импорт и отменить подтверждение. Текущие данные и действующие фото не должны измениться. Проверить повторный успешный импорт после отмены.
- [ ] Открыть повреждённую тестовую копию/копию с повреждённым фото. Должна появиться ошибка; рабочие данные не должны замениться.
- [ ] Быстро выполнить серию изменений и перезапустить. Никакое успешно сохранённое изменение не должно исчезнуть.

## Технические проверки — могу выполнять с вами

Эти пункты нельзя считать выполненными только по работе UI. Нативные сравнения не имеют отдельного пользовательского экрана.

- [ ] На debug APK подключить Chrome remote debugging (`chrome://inspect`) по USB и вызвать `await MPosCore.CatalogCutover.health()` в консоли WebView. Ожидается `comparison.ok:true`, `comparison.matches:true`, одинаковые количества товаров/категорий, `activeSource:'room'`, `roomCutoverAllowed:true`. Проверить после изменений, перезапуска и восстановления копии. Это необходимые, но не достаточные условия переключения: поля и порядок также сверяются с тестовыми данными.
- [ ] Проверить совпадение нативной копии настроек с UI. В консоли отправить `window.webkit.messageHandlers.settings.postMessage({action:'getPlatformSettings',requestId:'tablet-settings-check'})`; ответ приходит асинхронно в `window.__lastNativeSettingsResult`. После его получения сверить `snapshot.settings`; отсутствие немедленного ответа не означает ошибку.
- [ ] Явно включить диагностический SSE и сравнить один известный тестовый поток с браузером: Unicode, пробелы, несколько data-строк, пустые сообщения, именованные события. Затем обрыв связи и фон/возврат. Результаты last-hash сравнения сами по себе не доказывают совпадение всех событий двух асинхронных соединений.
- [ ] На тестовой установке проверить большой каталог/историю, нехватку места и остановку во время нативной записи. Данные JS должны оставаться пригодными; устаревший Room-снимок не должен выдавать успешное сравнение. Если условия отказа не создавались — записать «не проверено».
- [ ] Ограничения: полный файл больше 500 000 000 байт отклоняется, декодированное фото больше 2 000 000 байт отклоняется. Огромные тестовые файлы необязательны для обычной проверки на планшете; граничное чтение покрыто автоматическими тестами. Допустимый по размеру файл не гарантирует достаточную память на любом устройстве.

## Как прислать результаты

Для каждого пункта: номер/название, «прошло / ошибка / не проверено», ожидание и фактическое поведение. Указать модель планшета, Android, commit APK, ширину/модель принтера для печати. Пример: «Перезапуск после изменения товара — прошло, цена и порядок сохранились». Для ошибки описать шаги воспроизведения; не присылать секреты или рабочие резервные копии.

Последняя автоматическая проверка приложения: 150 JavaScript- и 161 JVM/Kotlin-тестов прошли, lint 0 ошибок/15 предупреждений, debug и minified unsigned release собраны. Эти результаты не заменяют приведённые физические проверки. Нативное хранение и частичная команда оплаты описаны в спецификациях 040–053; расчёт кассы нативной оплаты теперь Kotlin, остальные финансовые границы ещё частично JS.

## Дополнение 042–043 — сотрудники и смены

Основное хранение employees и shifts теперь Kotlin/Room. Полный JSON и исходные роли, поля сотрудника, финансовые значения и кассовые движения сохранены. Документ и индексы записываются атомарно; после переключения устаревшая legacy-копия не заменяет Room. Проверки доступа и финансовые расчёты остаются в JS — этот этап не заявляет перенос их движков.

Для итоговой ручной проверки:

- [ ] Создать и изменить сотрудников разных ролей, проверить вход и разрешённые/запрещённые действия после перезапуска.
- [ ] Открыть смену с начальной наличностью, внести/изъять деньги, оплатить наличными и картой, закрыть смену; сверить суммы и PNG-чек Telegram с iPad.
- [ ] Экспортировать и восстановить v13, перезапустить; проверить сотрудников, роли, смены и все кассовые движения.

После 042–043 хранение оплаченных заказов, строк и способов оплаты перенесено в 044. Полный перенос финансового движка требует отдельного этапа с проверкой округлений, возвратов и split payment.

## Дополнение 044 — оплаченные чеки

Orders теперь хранится в Kotlin/Room с атомарным обновлением документа, позиций и оплат. Исходная продажа, смешанная оплата, возврат и поля лояльности сохранены. Расчёты продолжают исполняться в JS. API пока записывает весь массив чеков; построчные команды и пагинация потребуют отдельного этапа. [Схема хранения, ограничения и ручные проверки](RECEIPT_STORAGE_RU.md).

## Дополнение 045 — отложенные заказы

Parked теперь хранится в Kotlin/Room: документ, заголовки и позиции записываются атомарно. Модификаторы, клиент, доставка, WEB-идентификаторы и признаки кухонной печати сохраняются целиком. ## Этап 086 — начисление/отмена и журнал лояльности

Kotlin строит payload и управляет claim/finish/recover; Room подтверждает sending до POST и итог до изменения памяти. OkHttp отправляет sale/reversal с deadline/cancel и без автоматического повтора. Живые попытки защищены от reconnect recovery; прерванные sending становятся durable pending.

Существующие триггеры лояльности и backend idempotency сохранены. Они не меняют правило доступности 033: остатки повторяются только после следующей сохранённой оплаты. Backup v13 и статусы внутри чеков сохранены. 353 JS / 278 JVM тестов прошли; lint 0 ошибок / 15 прежних предупреждений. Физическая приёмка pending. Следующая граница — 087 WEB acceptance/ready журнал и ACK. [Спецификация](../specs/086-native-loyalty-journal/spec.md).

Сохранённый бизнес-вопрос: прямой вызов начисления может повторно отправить уже synced чек, тогда как reversal synced пропускается; обычный retry выбирает только разрешённые состояния. Не меняем эту политику и серверную идемпотентность молча. JS ещё отвечает за исходные триггеры/оркестрацию до native UI/runtime cutover.

## Этап 087 — WEB журнал и подтверждения

webOrderAcceptances/webOrderReadyJournal стали основными документами Room, с одноразовым импортом и защитой от устаревших shadow writes. Kotlin проверяет durable local/pending перед ACK и сетевое подтверждение перед confirmed; изменения разных записей объединяются без потери соседних. Исправлен failure-window очистки: готовность удаляется только при confirmed в Room; события приёма очищаются по свежему Room журналу, а не по изменённому лишь в памяти объекту после failed save. V13/исходные printing/estimate/stock rules и retry triggers сохранены. Приём WEB items, кухня, UI и расписание восстановления ещё используют reviewed runtime; SSE/event ownership — следующий 088. 364 JS / 287 JVM тестов прошли; lint 0 ошибок / 15 прежних предупреждений. Физическая приёмка pending. [Спецификация](../specs/087-native-web-journals/spec.md).

Сохранённый бизнес-вопрос: кухня печатает до backend ACK; падение после физической печати до сохранения printed snapshot может повторить печать. Это отдельная внешняя граница 099, Room сам не гарантирует exactly-once принтер.

автоматического повтора нет. Создание/редактирование поставщиков и незащищённые
действия сохраняют прежние права; права лояльности на сервере не ужесточены.

**Согласованное пользователем правило:** после неподтверждённой корректировки
повтор возможен только после проверки актуального баланса. Нативная отметка
mpos_loyalty_adjustment_verification_v1 создаётся до запроса, сохраняется при
обрыве/timeout/5xx и после перезапуска. Она отдельно от кассового recovery и не
блокирует продажи. Успешный ответ/явное отклонение снимают её; при неопределённом
результате только успешный нативный GET баланса конкретной программы позволяет
вернуться к ручному вводу. Форма показывает актуальный прогресс/подарки и сбрасывает
дельты; проверка баланса не отправляет корректировку. Старый token не снимает
отметку новой операции. Отметка не содержит пароль/токен Telegram/device key;
внутренний служебный ключ не меняет формат бизнес-данных backup v13.
