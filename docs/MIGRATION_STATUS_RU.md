# Статус миграции M POS Android и проверки на планшете

Срез: 6 октября 2026 года, после спецификаций 040–046. Пользователь разрешил нативные переключения сразу после автоматических проверок; комплексная ручная приёмка перенесена на конец миграции. Основание: дорожная карта, матрица совместимости, спецификации 002–039 и текущая реализация. «Реализовано» означает наличие кода; «принято» требует результатов физических проверок.

Для доли кода учитываются 65 production Kotlin-файлов в app/src/main/java, 36 JS-файлов в app/src/main/assets/pos и встроенный исполняемый JavaScript в pos.html. Не учитываются тесты, документация, HTML-разметка, CSS, ресурсы, Gradle и сгенерированный код. Используются байты UTF-8, чтобы разное форматирование и короткие JS-строки не превращались в искусственный процент по количеству строк. Комментарии остаются в объёме соответствующих исходников.

26,88% — **доля языка, не оценка завершённости миграции по сложности, ценности или трудозатратам**. Точный общий процент выполнения нельзя вывести без согласованной декомпозиции и весов задач. Основное хранение уже переключено для девяти документов: products, layout, posNavigation, employees, shifts, orders, parked, currentOrderSession и criticalStorageJournal; это не перенос финансовых движков или Compose-экранов. Многие Kotlin-платформенные функции существовали до последних этапов; они включены в текущий срез, а не приписаны последним изменениям.

Сотрудники и права доступа пока также обслуживаются существующим runtime: P2 уже перенёс хранение сотрудников в Kotlin, но не переносит авторизацию автоматически. Для экранов зала/столов/бронирований нужна отдельная детализация после стабилизации данных; готовой нативной реализации и утверждённой отдельной спецификации для них сейчас нет. Это оставшиеся части существующего приложения, а не молча завершённые этапы.

Не планируем переписывать всё сразу, заменять рабочий нативный ESC/POS, добавлять другой cross-platform runtime, автоматическую синхронизацию каталога или менять v13 без отдельной миграции.

Политика остатков после ошибки реализована Android JS-адаптером (033), **не переносом на Kotlin**: повтор только после следующей сохранённой оплаты. Фотографический отчёт смены (034) — Kotlin-представление, **не нативный финансовый движок смены**. Последние 035–039 укрепляют уже начатые нативные границы.

## Что проверить сейчас — обычные действия на планшете

Тестировать на отдельной тестовой установке с синтетическими данными. Для каждой проверки записать результат. Не восстанавливать тестовую копию поверх рабочей кассы. Для этого среза нужен APK с изменениями 040–046: старые APK до этих спецификаций ещё использовали каталог/раскладку как сравнительные копии. В GitHub Actions артефакт называется M-POS-Android-debug; workflow теперь запускает JVM-тесты и обе сборки; наличие успешной загрузки конкретного артефакта нужно проверить в выбранном запуске. ## Технические проверки — могу выполнять с вами

Эти пункты нельзя считать выполненными только по работе UI. Нативные сравнения не имеют отдельного пользовательского экрана.

- [ ] На debug APK подключить Chrome remote debugging (`chrome://inspect`) по USB и вызвать `await MPosCore.CatalogCutover.health()` в консоли WebView. Ожидается `comparison.ok:true`, `comparison.matches:true`, одинаковые количества товаров/категорий, `activeSource:'room'`, `roomCutoverAllowed:true`. Проверить после изменений, перезапуска и восстановления копии. Это необходимые, но не достаточные условия переключения: поля и порядок также сверяются с тестовыми данными.
- [ ] Проверить совпадение нативной копии настроек с UI. В консоли отправить `window.webkit.messageHandlers.settings.postMessage({action:'getPlatformSettings',requestId:'tablet-settings-check'})`; ответ приходит асинхронно в `window.__lastNativeSettingsResult`. После его получения сверить `snapshot.settings`; отсутствие немедленного ответа не означает ошибку.
- [ ] Явно включить диагностический SSE и сравнить один известный тестовый поток с браузером: Unicode, пробелы, несколько data-строк, пустые сообщения, именованные события. Затем обрыв связи и фон/возврат. Результаты last-hash сравнения сами по себе не доказывают совпадение всех событий двух асинхронных соединений.
- [ ] На тестовой установке проверить большой каталог/историю, нехватку места и остановку во время нативной записи. Данные JS должны оставаться пригодными; устаревший Room-снимок не должен выдавать успешное сравнение. Если условия отказа не создавались — записать «не проверено».
- [ ] Ограничения: полный файл больше 500 000 000 байт отклоняется, декодированное фото больше 2 000 000 байт отклоняется. Огромные тестовые файлы необязательны для обычной проверки на планшете; граничное чтение покрыто автоматическими тестами. Допустимый по размеру файл не гарантирует достаточную память на любом устройстве.

## Как прислать результаты

Для каждого пункта: номер/название, «прошло / ошибка / не проверено», ожидание и фактическое поведение. Указать модель планшета, Android, commit APK, ширину/модель принтера для печати. Пример: «Перезапуск после изменения товара — прошло, цена и порядок сохранились». Для ошибки описать шаги воспроизведения; не присылать секреты или рабочие резервные копии.

Последняя автоматическая проверка приложения: 93 JavaScript- и 116 JVM/Kotlin-тестов прошли, lint 0 ошибок/15 предупреждений, debug и minified unsigned release собраны. Эти результаты не заменяют приведённые физические проверки. Нативный переход каталога/раскладки/навигации/сотрудников/смен описан в спецификациях 040–046; финансовые расчёты остаются в JS.

## Дополнение 042–043 — сотрудники и смены

Основное хранение employees и shifts теперь Kotlin/Room. Полный JSON и исходные роли, поля сотрудника, финансовые значения и кассовые движения сохранены. Документ и индексы записываются атомарно; после переключения устаревшая legacy-копия не заменяет Room. Проверки доступа и финансовые расчёты остаются в JS — этот этап не заявляет перенос их движков.

Для итоговой ручной проверки:

- [ ] Создать и изменить сотрудников разных ролей, проверить вход и разрешённые/запрещённые действия после перезапуска.
- [ ] Открыть смену с начальной наличностью, внести/изъять деньги, оплатить наличными и картой, закрыть смену; сверить суммы и PNG-чек Telegram с iPad.
- [ ] Экспортировать и восстановить v13, перезапустить; проверить сотрудников, роли, смены и все кассовые движения.

## Дополнение 044 — оплаченные чеки

Orders теперь хранится в Kotlin/Room с атомарным обновлением документа, позиций и оплат. Исходная продажа, смешанная оплата, возврат и поля лояльности сохранены. Расчёты продолжают исполняться в JS. API пока записывает весь массив чеков; построчные команды и пагинация потребуют отдельного этапа. [Схема хранения, ограничения и ручные проверки](RECEIPT_STORAGE_RU.md).

## Дополнение 045 — отложенные заказы

Parked теперь хранится в Kotlin/Room: документ, заголовки и позиции записываются атомарно. Модификаторы, клиент, доставка, WEB-идентификаторы и признаки кухонной печати сохраняются целиком. Реальные park/resume-команды проверены, включая сохранение корзины до native commit и восстановление после неудачного resume. Текущая сессия и междокументный журнал пока legacy; расчёты и печатные триггеры остаются в JS.

Для итоговой проверки: отложить заказ с доставкой/модификаторами/клиентом и кухонной печатью, принудительно остановить приложение, открыть заказ обратно, сверить все поля; повторить с WEB-заказом. Проверить удаление, бэкап v13 и перезапуск после переноса в корзину.

Следующая граница: хранение текущей сессии и критического журнала восстановления в Kotlin, затем отдельные команды записи чека/заказа вместо полного массива.

## Дополнение 046 — текущая корзина и журнал восстановления

CurrentOrderSession и criticalStorageJournal теперь основные документы Kotlin/Room с атомарными индексами и независимыми маркерами миграции. Исходная корзина, модификаторы, доставка, клиент, WEB, split-черновик и печатные признаки сохраняются целиком. Ошибка чтения журнала блокирует восстановление и новые критические операции, а не принимается за пустой журнал. Неудачная очистка оставляет снимки для повтора.

При итоговой проверке перезапустить с незавершённым заказом и после прерванной оплаты/откладывания/восстановления корзины; сверить чек, склад, смену и отсутствие повторной операции. Проверить v13-экспорт/импорт текущей сессии. Применение журнала и бизнес-расчёты ещё JS; это не единая междокументная SQL-транзакция.

Следующий этап — команды записи отдельного чека/заказа и постраничная история. Native journal уже обеспечивает основу для восстановления этих операций.
