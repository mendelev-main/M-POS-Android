Нативная отрисовка экрана не означает независимость от JS: некоторые контроллеры получают модель из скрытого HTML и отправляют действия обратно в DOM. ## Каким должно стать приложение

Целевая цепочка: **нативный UI → Kotlin state/read models → Kotlin расчёты и команды → локальная Room transaction → подтверждённое UI state → разрешённые внешние эффекты**. Запуск, касса, склад, чеки, рецептуры, смены и восстановление не требуют интернета; сеть не блокирует локальную продажу. Ключи и backup v13 сохраняют совместимость до явно проверенной миграции. Принтер — отдельный локальный транспорт, Telegram/WEB — отдельные внешние клиенты.

В production не должно остаться построения моделей через HTML, `node.click()`, `evaluateJavascript` бизнес-диспетчеризации или скрытого WebView. POS остаётся источником данных для Backend → Web/Mini App. Каталог синхронизируется вручную. Availability после ошибки повторяется только после следующей успешно сохранённой оплаты; запуск/reconnect/добавление в корзину не являются повтором отправки.

**Расчёты:** уже используются `MPosPricingEngine`, `MPosCartTotalsEngine`, `MPosRecipeConsumptionEngine`, `MPosStockPreflightRepository` и другие Kotlin engines. В pricing текущий код использует `Double` и совместимые функции округления, а не автоматически BigDecimal/целые копейки. Полная миграция runtime сама по себе не меняет принятую арифметику: менять денежное представление можно отдельной совместимой задачей с проверками сумм/округления.

**Визуализация:** текущие production экраны — программно создаваемые Android Views/widgets (`LinearLayout`, `TextView`, кнопки и др.) и `MPosNativeTheme`. Compose не является текущим UI runtime: в app нет Compose dependency/build configuration. Переход на Kotlin не требует перехода на Compose. Room хранит данные, Kotlin engines считают, Android Views отображают.

**Изменение дизайна в будущем:** возможно. Общие цвета/типографика/размеры легче менять через shared theme; перестановку блоков нужно делать в соответствующих контроллерах; новые сценарии требуют также state/commands/tests. Сейчас изменение модели экрана часто затрагивает и JS extraction, и Kotlin controller. После 109.09–109.14 эта связь исчезнет. Полный новый дизайн всё равно не станет одной настройкой: есть много экранов и программная разметка. Compose — возможный отдельный выбор, не условие завершения этого плана.

## Динамический остаток на карточках

Подтверждённый текущий путь: `pos-navigation.js` вызывает `availableStock(p)`; `pos.html` для simple возвращает `p.stock`, для составного считает возможность производства по ингредиентам. Текущая корзина из этого значения **не вычитается**. Нативный workspace читает готовую строку `.pcard-stock` из DOM. Следовательно, непрерывное уменьшение цифры после добавления товара в корзину этим путём не реализовано.

При этом уже есть отдельный Kotlin stock preflight и решение изменения количества: это защита от нехватки при изменении заказа/оплате, а не готовая реактивная карточка остатка.

Нужная модель в 109.09:
- Разделить **фактический складской остаток** и **доступно с учётом текущей корзины**.
- Пример: на складе 10, в корзине 2 → доступно 8; убрали одну → 9. До продажи физический склад не списывается.
- Для рецептур и модификаторов вычитать потребление общих ингредиентов всей корзиной, а затем считать доступное число порций. Простого `stock - qty этого товара` недостаточно.
- Изменение корзины или Room данных пересчитывает нативную модель и обновляет карточки/кнопки; поздний расчёт от старого snapshot не применяется.
- Commit оплаты повторно проверяет актуальные данные и списывает один раз; отмена/возврат/восстановление проходят соответствующие команды.
- Определить отдельную политику для parked/WEB/split/нескольких устройств: локальная цифра в корзине не равна глобальному резерву и не даёт межустройственной гарантии.

Кейсы проверки: simple, общие ингредиенты двух блюд, модификаторы, дробные единицы, noStockTracking, удаление/очистка/отмена, восстановление, нулевой остаток, concurrent stock change, split без двойного вычета. Это критерии нужной реализации, а не уже выполненные проверки.

## Почему могут не работать принтер, бот и сайт

### Telegram: найденный конкретный дефект

`MainActivity.telegramResult()` вызывает `window.handleTelegramResult(...)`, но в assets нет такого обработчика; `pos.html` определяет `window.onTelegramResult(...)`. Канал bridge `telegram` зарегистрирован, Kotlin client действительно выполняет HTTP запросы. Дефект относится к возврату результата в UI: успешная отправка и её ошибка могут не отображаться. Он не доказывает отсутствие самого HTTP запроса. Результаты monthly/shift-close имеют другие callbacks, это не автоматическое объяснение всех Telegram сценариев.

Исправление: согласовать callback, проверить success/failure/timeout и delivery до интерфейса. Отдельно проверить настройки botToken/chatId/threadId, доступ бота к группе, права, Start личного получателя и синхронизацию backend-настроек. `sendMessage` сейчас сворачивает отказ в `Telegram HTTP <code>`, теряя полезную безопасную причину; диагностику стоит улучшить без токенов и персональных данных. Токен не нужен в чате.

### Тестовый WEB-заказ: отдельный разрыв async обратной связи

`Web/js/features/web-orders.js:testWebOrder()` запускает fetch к `/api/orders/test`, но не возвращает Promise. В `native-settings-ui.js` этот обработчик также отсутствует среди отслеживаемых settings operations. Нативный `submit()` показывает «Выполнение…», затем общий formResult может очистить сообщение до окончания fetch; поздний результат идёт только в browser `flash`. Форма при этом отображается native AlertDialog поверх WebView, её DOM скрыт. Это подтверждённая по коду неполная передача асинхронного результата в native форму, соответствующая сообщению о кнопке без реакции. Сам факт выполнения HTTP запроса на планшете пока не подтверждён.

Исправление: вернуть Promise из теста, связать pending/result с native form token, показать success/error/timeout непосредственно в форме, защитить повторные нажатия и поздний ответ после закрытия формы. Проверять статусы `/api/orders/test` отдельно от `/health`; не создавать тестовые заказы на рабочем backend только ради этого аудита.

### Принтер: установленные ограничения

Транспорт `EscPosPrinter` отправляет ESC/POS через TCP socket на IPv4; JS конфигурация фиксирует порт **9100**. USB/Bluetooth транспорт отсутствует. Если пользователь подключает таким способом, это неподдерживаемая функция, а не отсутствие разрешения на LAN. `network_ready` означает готовность сервиса, а не установленную связь с принтером; фактическое соединение открывается при задании.

Пользователь подтвердил Wi-Fi в локальной сети: отсутствие USB/Bluetooth не является объяснением данного случая. Для LAN проверить адрес именно принтера, тот же маршрутизируемый сегмент, открытый порт, отсутствие guest/client isolation и поддержку ESC/POS. Тест из формы сначала ждёт native disk acknowledgement настроек, затем отправляет задание — эта граница в коде есть. Ошибки socket/queue/storage могут показываться общей строкой, поэтому по одному сообщению невозможно назвать причину. При неопределённом результате нельзя автоматически печатать повторно.

### Backend/сайт: сервер не выглядит полностью недоступным

GET к дефолтному `https://project-dubrovno.up.railway.app/health` на момент проверки вернул **HTTP 200**, `{ok:true,service:...}` и `Access-Control-Allow-Origin: *`. Это проверка из среды разработчика, не с планшета и не авторизованных endpoint'ов. URL у пользователя может быть другим. `/health` не доказывает регистрацию deviceKey, SSE, ACK, каталог, WEB заказ или Telegram backend settings.

`testBackendConnection` ещё делает browser `fetch('/health')`; PUT Telegram settings также остаётся browser fetch. Ряд доменных операций уже использует OkHttp. Следует отдельно проверить HTTPS URL, сеть/DNS/TLS планшета, точный статус нужного endpoint, ключ устройства/серверную регистрацию и цепочку POS → Backend → Web. Возможные конфигурационные/сетевые причины пока гипотезы; общей доказанной причины всех трёх сбоев нет. Связь сайта с каталогом также требует ручной синхронизации, автоматическая отправка не включается самим запуском приложения.

## Как чинить и чего ждать по срокам

Текущие сбои нужно разбирать **сейчас**, не ждать 109.16/109.17. Эти подэтапы убирают остаток JS orchestration, а не разрешают откладывать регрессии уже реализованных transport boundaries.

Порядок: подтвердить установленный APK → воспроизвести три отдельных теста и сохранить безопасные ошибки → устранить Telegram callback и async feedback WEB-теста → отделить фактические сетевые ошибки от UI/настроек → проверить реальный LAN тест и backend endpoints → закрепить regression checks. Состояние продаж и journal не очищать для экспериментов.

Callback — локальная небольшая правка, но проверка доставки требует реальной группы. Ошибочный LAN адрес/порт/права Telegram могут решаться настройкой; USB/Bluetooth, новый backend контракт или потеря native settings потребуют другого объёма разработки. Фиксировать срок в часах/днях до версии APK, способа подключения и текстов ошибок было бы необоснованно. Общий срок миграции также нельзя вывести из 86,82%: оставшиеся подэтапы неодинаковы и включают серьёзные startup/recovery/effects границы.

Для точного диагноза нужны версия/дата APK, Android версия, LAN/USB/Bluetooth принтера, точные сообщения после каждого теста и безопасная диагностика. Штатный diagnostic export содержит ограниченный журнал и версию, а не полный HTTP/socket trace; его отсутствие подробностей не опровергает сбой. Пароли, токены, deviceKey и рабочие резервные копии не присылать.
