# Хранение чеков

## Рекомендуемая модель

| Таблица | Назначение |
|---|---|
| Чеки | Одна запись на чек: ID, номер, смена, сотрудник, дата, исходная сумма и данные продажи |
| Позиции чека | Строки с историческими ценами, количеством, скидками и составом; связаны с ID чека |
| Оплаты | Отдельные части оплаты: наличные/карта, сумма, внесённые деньги и сдача; связаны с ID чека |
| Операции возврата — следующий этап | История возвратов с суммами, позициями и сменой; исходная продажа сохраняется |

Состояние расчётов, печати и внешней отправки — независимые вещи. Один общий status или набор несогласованных флагов не должны определять всё одновременно. Ошибка принтера или лояльности не отменяет сохранённую оплату. Повторные попытки отправки относятся к внешней операции, а не к новому чеку.

## Реализовано в 044

Основное хранение orders теперь Kotlin/Room. В существующей схеме 12 есть таблицы order_projection, order_line_projection и payment_projection. Полный JSON orders хранится как основной совместимый документ; эти три таблицы — вспомогательные индексы. Документ и все индексы коммитятся вместе, после чего обновляется вторичная legacy-копия.

Это переходный этап: API ещё передаёт весь массив чеков и обновляет все его индексы при записи. Построчные команды и пагинация истории пока не реализованы. Следующий этап должен сделать отдельный чек единицей записи, сохранив v13 через адаптер импорта/экспорта и паритет платежного движка.

## Действующая бизнес-логика сохранена

Сейчас возможен полный возврат один раз: поля returnedAt, returnedShiftId и returnAmount остаются на исходном чеке. Сумма продажи, позиции и оплаты не заменяются возвратом. При смешанной оплате из текущей кассовой смены списывается наличная часть, карточная возвращается отдельно через банковский терминал. Частичные возвраты и подтверждение банковского возврата автоматически не добавлены.

Для будущего рефакторинга: старые чеки без stockConsumption восстанавливают склад по существующему legacy-пути, включая текущий рецепт составного товара. При изменении рецепта после продажи это отличается от возврата по историческому списанию. Поведение сохранено; нужна отдельная бизнес-политика для старых чеков перед его изменением.

## Итоговая ручная проверка

- [ ] Продать наличными, картой и смешанной оплатой; перезапустить, сверить номер, позиции, скидки, суммы, сдачу и состав оплаты.
- [ ] Вернуть чек в другой открытой смене, проверить склад, наличную часть и исходную продажу; повторный возврат должен блокироваться.
- [ ] Проверить возврат при недостатке наличных, старый чек без исторического списания и изменение рецепта после продажи.
- [ ] Проверить лояльность/повторную печать после перезапуска, экспорт и восстановление v13.
- [ ] Проверить крупный архив, время сохранения и историю; этот этап не обещает улучшение скорости за счёт построчной записи.

## Реализовано в 047

Для корректных архивов полные чеки теперь отдельные основные записи Room; позиции и оплаты связаны по ID. Новая продажа/возврат обновляет только изменившиеся записи, вторичный legacy-массив больше не переписывается. Native API поддерживает отдельную запись с проверкой ревизии. История читает SQL-страницы по 50 записей и может показывать архив дальше 300 чеков. Прежние документы мигрируют атомарно; некорректные ID сохраняются через совместимый режим полного документа.

Платёжные/возвратные команды JS ещё передают весь массив, журнал содержит полный снимок, а startup и расчёты загружают весь архив. Эти расходы пока остаются; полный перенос бизнес-команд нужен для их устранения. После переключения построчного хранения откат требует актуального полного экспорта/бэкапа, а не старой legacy-копии.
