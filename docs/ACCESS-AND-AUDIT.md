# Доступ, секреты и аудит действий

Статус: проектные требования; окончательная матрица ролей и способ входа остаются открыты до 05. Здесь не задаются юридические правила consent/сроков хранения. Источник поведения Web: pinned `docs/ADMINISTRATION_SESSION_RU.md`, feature guards и `android-safety.js`; native UI не обязан копировать визуальный контур Web.

## Кто действует и от чьего имени

Различаются actor (инициатор команды), employeeId текущего кассира, shiftId, runtime adminSession и integration binding. Администраторский вход не меняет кассира и не переносит на него историю. Исторический receipt хранит snapshot нужных полей автора; переименование сотрудника не меняет документ задним числом.

Web разделяет admin session и смену: новый runtime требует входа, подтверждение изменяющего действия проверяет доступ повторно. Native сохраняет этот смысл. Activity recreation не должна сама расширять права, process death/logout сбрасывают admin session. Поведение сворачивания/timeout/блокировки планшета утверждается перед 05; автоматический timeout пока не считается реализованным.

До 05 приложение имеет явно обозначенный single-owner режим без разграничения сотрудников. В документации/релизе нельзя обещать кассирские ограничения, пока authentication и authorization не реализованы. Если до 05 требуется эксплуатация несколькими сотрудниками, минимальный доступ переносится раньше отдельным изменением плана.

## Предлагаемые capabilities для согласования

| Capability | Назначение | Базовый кандидат на ограничение |
|---|---|---|
| catalog.read / order.edit | чтение каталога, сбор заказа | оператор |
| catalog.write / layout.write | товары/категории/раскладка | владелец/администратор |
| sale.commit / shift.cash | продажа и движения наличных в разрешённой смене | кассир по активной смене |
| sale.manualPrice / sale.discount / sale.refund | ручная цена, скидка, возврат | отдельное разрешение, не следствие order.edit |
| inventory.write / receiving.commit | корректировка/приёмка | отдельное складское полномочие |
| employees.manage / roles.manage | сотрудники и права | администратор |
| reports.read / reports.export | просмотр и выдача отчётов | отдельно с scope данных |
| backup.export / backup.restore | доступ к полному набору данных | отдельное критическое полномочие |
| integration.configure / integration.test | привязка сайта, принтер, Telegram | отдельное административное действие |
| app.update | запуск системной установки | отдельная политика; 00.1 сейчас без ролевого ограничения |

Это список командных возможностей, не утверждённое распределение фиксированных ролей. Не вводить имплицитное «закрытая/старая смена администратора даёт все права». Сервер дополнительно проверяет свою авторизацию; локальная роль не выдаёт server полномочия.

Use case получает trusted actor context из auth provider, не произвольное role поле UI. Проверка повторяется непосредственно перед изменением. Открытая форма не даёт вечного доступа: logout/отзыв прав между открытием и сохранением приводит к отказу. Уже committed действие остаётся фактом истории. UI показывает доступность действий, но не заменяет command guard.

## Секреты и персональные данные

Секреты API/устройства/PIN и signing JKS — разные классы. APK signing key существует только в release инфраструктуре/private backup, не на планшете. Device credential выдаётся/меняется по server contract и используется через secret reference; outbox не дублирует его в каждой записи. Локальный verifier пароля/PIN требует отдельного выбора защищённого хранения/проверки; plaintext в Room/preferences/backup запрещён.

Сброс/потеря ключа secret store не удаляет продажи; интеграция переходит в «Требуется повторная привязка». Restore на другом устройстве не выдаёт ему старые полномочия автоматически. Настройки системного Android backup/extraction для бизнес-БД/секретов проверяются до первого эксплуатационного релиза с Room; текущий механизм пользовательского backup не считается равным системному.

Контакты клиентов показываются только там, где нужны действию. Сырые телефоны, username, состав реального backup и ответы с персональными полями не включаются в telemetry/test fixtures. Masked лог не является разрешением экспортировать весь request. Consent текст/правовое основание/срок хранения определяются владельцем продукта до 06, а не выдумываются из технического поля.

## Аудит и диагностика — разные журналы

AuditEvent для принятой критической команды содержит eventId, commandId, actor/employee/shift references, action, targetId, outcome, timestamp/zone context и безопасное описание изменения. Событие успешной команды пишется в той же transaction, что и её результат. Audit не содержит пароль, device key или полный payload клиента.

Отказы авторизации/сети можно фиксировать в ограниченном диагностическом журнале; сбой такого логирования не превращает отказ в успешную команду. Локальный audit не является криптографическим доказательством против владельца/root устройства. Изменения audit через пользовательский редактор не предусмотрены; экспорт зависит от отдельного права и scope.

Диагностический пакет по явному действию содержит app/schema versions, ID операции, типы ошибок, безопасные статусы и временные метки. Объём/срок удержания ограничиваются до включения, большие файлы ротируются. Удаление диагностики не удаляет receipt/audit/operation results. Реальные backups/keystore не прикладываются к issue автоматически.

## Критерии приёмки

ACC-01: кассир не может вызвать admin use case напрямую. ACC-02: logout после открытия формы блокирует save. ACC-03: процесс умер → admin session отсутствует, смена/receipt сохранены. ACC-04: проверка logs/backup/outbox не находит secret fixtures. ACC-05: restore не восстанавливает активную admin session/device credential. ACC-06: успешно изменённый объект и audit появляются вместе либо оба откатываются. ACC-07: потерянный secret блокирует интеграцию, сохраняя локальную кассу. Связь H03/H04, C04, B01/B02, N01/N06; всё planned.
