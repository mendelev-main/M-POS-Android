## Рабочий путь

Настройки → Резервная копия → Выбрать Web-копию. В отдельной Room базе создаются каталог, фото, раскладка, сотрудники, поставщики, смены, текущий и отложенные заказы. Проверяются исходные количества/цены/расход, кассовые факты и независимая native-копия кандидата. Неподдерживаемые или неоднозначные данные прекращают подготовку, не меняя рабочую базу.

После просмотра пользователь подтверждает, что отложенные интеграции не включаются в работу. «Создать защитную копию и подготовить замену» передаёт проверенный кандидат существующему native recovery. Далее — отдельное подтверждение полной замены и дополнительное подтверждение активного target. Применение использует прежний generation/write-seal/restart протокол; после перезапуска вход администратора сброшен. Старые chooser/формы не заимствуют новую административную сессию.

Оригинал Web хранится побайтно, с BOM/пробелами/фото, в ограниченных base64 chunks `web-original-source`. Hash, размер, комплектность и parser проверяются при восстановлении. Исходный файл может содержать контакты и настройки; он остаётся в приватном dataset и последующих native-копиях, не выводится в журнал и не запускает интеграции.

## Операционные контракты

- AD01: cart codec3 читает1/2/3. `sellingBasis=recipe-batch` отличает количество проданных порций от физических единиц рецепта. Native references — фактические начальные ревизии кандидата, не вымышленные Web revisions. Неизвестные source basePrice/manual сохраняются null, без переписывания исходных фактов.
- AD02: split-progress3 содержит immutable source origin + соответствие стабильных native part IDs исходным оплаченных позициям. Source40 не получает фиктивный operation_result. Новые60 получают реальное подтверждение; финальный native чек/склад/погашение прогресса выполняются одной транзакцией. Подтверждённые части не редактируются. Старые split1/2 читаются прежним способом.
- AD03: independent restore validation требует полный оригинал, соответствующий evidence, кассовый baseline и действующий либо завершённый native adoption. Evidence-only candidate по-прежнему не допускается. Повтор native команды не принимает деньги/не списывает склад снова.
- AD04: `web-import-baseline` сохраняет вычисленное движение завершённых source cash фактов отдельно от openingCash. Pending40 не добавляется в этот baseline; финальный native cash40 учитывается один раз. Source courier/refund факты не дополняются несуществующими операциями.
- AD05: `web-catalog-basis` сохраняет batch semantics для последующих продаж импортированных составных товаров. Цена10 за рецепт выходом3кг остаётся10 за порцию, запрос на склад —3кг. Обычные native товары сохраняют прежнюю семантику физических единиц. Отчёт по новым продажам различает `batch` и `kg`.
- AD06: скидки/доставка исходного неоплаченного или отложенного заказа хранятся в `web-order-defaults`, без команд оплаты. После возобновления служат начальными полями формы; актуальный сохранённый checkout имеет приоритет. Доставка переносит исходные адрес/телефон. Отсутствующие исторические сведения не заполняются текущим каталогом.
- UI01: original chooser authorization, explicit unsupported confirmation, защитная копия, active-target confirmation, stale fingerprint, существующий restart protocol.

## Ограничения, которые нельзя скрывать

- Исторические Web чеки/возвраты/складские документы сохраняются в validated legacy archive и полном оригинале, **ещё не подключены к native спискам операций, аналитике и возвратам**. В preview, истории чеков и аналитике это явно написано. Это не завершённый полный перенос истории.
- Активная инвентаризация и черновики приёмки пока **отказывают в применении**, а не молча сбрасываются или считаются отложенными модулями. Их операционное преобразование ещё требуется. Ожидаемые закупки без таких черновиков теперь преобразуются по WEB-PENDING-PURCHASE-F02.md; операционный путь прошёл CI42282692301 (304JVM/294API36); последняя pure-проверка противоречивой истории проверена отдельно локально305JVM.
- Неизвестные units/cost/stock, неподтверждённая принадлежность оплаты смене, all-paid/possible receipt overlap, неизвестная оплата лояльностью и несовпадающее денежное округление блокируются. Объяснение не является автоматическим исправлением source.
- Таймзона импортированных смен закреплена как Europe/Minsk; оригинал сохраняется. Нет утверждения о наличии source zoneId.
- Физический планшет, большие пользовательские копии, реальные disk-full/power-loss не проверены. Нет релиза/main merge.

## Следующие обязательные части до полной готовности

1. Операционная совместимость складских незавершённых документов с provenance, без поддельных команд и повторного проведения.
2. Подключение legacy истории к просмотру, отчётам и допустимым действиям, с явным unknown coverage; сохранение денег/исторического расхода и исходной даты возврата.
3. End-to-end Web activation/restart/source40 + native60/target30 protection, UI/API36, recovery/retention, операторская и планшетная приёмка.

Наличие кнопки применения не закрывает эти пункты. Статусы CI/device ставятся только после наблюдаемого результата.
