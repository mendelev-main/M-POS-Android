13.11.2026 владелец разрешил локально подготовить новый backend API общей истории; публикация/развёртывание сервера отдельно. База backend checkout:75813b31bc398b1849a5c6a5245481a28c6b8cd1. Native работает через существующие URL/device key/ordersPath, без новых зашитых адресов.

## Реализованный объём EV01–EV05

- EV01: «Текущие / История / Обновить» в общем окне событий. Обновление текущих читает `GET {ordersPath}/current`. Только `complete:true` разрешает атомарно заменить реконструируемый encrypted inbox. Принятые другой кассой заказы исчезают из текущих; запоздалый старый SSE не возвращает их после refresh/restart. Явный новый полный снимок может восстановить реально переоткрытый на сервере заказ. Старый SSE с окном20 остаётся механизмом поступления новых событий, а не доказательством удаления отсутствующего заказа.
- EV02: общая серверная история `GET {ordersPath}/history?limit=5&cursor=…`. Загружается5записей, затем «Показать5следующих». LazyColumn не компонует всю историю. При refresh первая страница перечитывается; порядок/курсор серверные, без offset. Новые записи не сдвигают следующую страницу.
- EV03: статусы Новый/Принят/Готовится/Готов/Отменён, «Оплачен» по server web_paid_at. Историческая карточка содержит состав/стоимость/детали и статус; в ней нет принятия, выбора ETA или удаления. Просмотр не вызывает локальные кассовые/складские/сетевые write-операции.
- EV04: ошибки/неполный ответ/401/403/404 не очищают текущие данные и не продвигают курсор. Повторный тап не запускает параллельные страницы. При смене URL/key/dataset текущая история сбрасывается; старый ответ не может опубликовать историю другой организации.
- EV05: старый backend без маршрутов получает явное сообщение об обновлении backend, без маскировки пустой историей. Полный current ограничен1000заказов и1MBHTTPответа; при превышении сохранённый inbox остаётся прежним. Серверный API истории/indexmigration подготовлены локально в соседнем M-Pos-Backend; рабочий сервер не изменён.

## EV06 — согласованный макет «Карточки»,14.11.2026

Implemented locally. Список текущих заказов и история по5 записей, заголовок с обновлением/закрытием; карточки с номером, клиентом, датой, составом, суммой, способом получения и статусом. В деталях «Назад» стоит в одной строке с обновлением/закрытием; отдельная надпись «Заказ с сайта» удалена. Полный телефон, адрес и комментарий показаны текстом справа от соответствующих иконок, без маски и без тестовых данных. Стикер оплаты независим от статуса: «Оплачен» при web_paid_at, иначе «Наличными». web_paid_at заполняется в том числе кассовым settlement (миграция015_receipt_only_loyalty.sql); это не признак оплаты на сайте. API не передаёт источник/способ завершённой оплаты; не выводим по нему «Оплачен на сайте» или «Карта».

Когда будет готов:5/15/30/40мин, ниже1час/2часа, затем ручные минуты1–1440. Быстрые5/15/30/40 сохраняют существующие tokens; остальные длительности на момент подтверждения преобразуются в at:HH:mm в часовом поясе планшета. Backend принимает этот контракт без изменения маршрутов/схемы. По существующему протоколу дата готовности не передаётся: переход через полночь сохраняет часы/минуты, но не отдельную дату. История остаётся read-only; администраторское тихое удаление и локальное принятие используют прежние guards/репозитории.

Утверждённый макет заменяет прежнюю Web-компоновку ON02; это намеренное изменение владельца, pinned reference не обновлялся. Ручная визуальная приёмка на планшете pending; наличие кода/компиляции не доказывает pixel parity. Push/release не выполняются в этой итерации.
