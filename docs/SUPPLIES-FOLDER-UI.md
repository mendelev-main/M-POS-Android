# Закладки поставок — 12.11.2026

Источник этого оформления — утверждённый владельцем макет `supplies-simple.html`, а не изменение pinned Web. Новый shared variant `MposFolderPanel` применяется к заказам поставщикам и открытой приёмке по заказу. Остальные экраны приложения не меняются автоматически.

## Контракт

- SF01 implemented locally: без дополнительного заголовка; «Поставки», «Новый заказ», «История» равной ширины, занимают всю строку (уточнение владельца после выбора первого варианта). Первая вкладка синяя, вторая зелёная, третья жёлтая. Цветная плашка заполняет вкладку, активная закладка соединяется с поверхностью панели.
- SF02 implemented locally: единый Canvas Path рисует панель и активную закладку, верхние/нижние радиусы18dp, верхние углы закладки18dp и вогнутые плечи10dp. Крайние закладки отступают28dp от углов панели, промежутки20dp; нет наложенных рамок/градиентов на стыке. Высота56dp, внутренняя плашка radius10dp, touch targets не менее48dp. Light/dark палитры явные, состояние выбранной вкладки доступно через semantics.
- SF03 implemented locally: вкладки взаимоисключающие. По умолчанию ожидаемые поставки, «История» показывает сохранённые заказы, «Новый заказ» существующую форму. Переключение не очищает ViewModel/черновик. Из ожидаемого заказа доступна команда «Принять».
- SF04 implemented locally: приёмка по заказу использует те же закладки. Переход в другую вкладку сначала сохраняет и закрывает форму существующим `saveAndExit`; при ошибке остаётся текущая форма. Подтверждение прихода и транзакции склада не меняются.

Уточнение владельца: перенос внутренних вкладок также обязателен. Следующие пункты заменяют прежнюю границу «только оформление закладок».

- SF05 implemented locally: единый список отдельных карточек radius16/border1/padding14/gap12. На карточке поставщик/date/count, статусы «Ожидает поставки» жёлтый, «Принята» зелёный, «Отменена» красный. Только при историческом недостатке дополнительный красный «Недовоз»; метки полной доставки нет, подтверждённый перевес недовозом не считается. Нажатие карточки раскрывает товары (одна за раз), суммы берутся из сохранённого прихода. «Принять» зелёная, «Продолжить» жёлтая; ⋯ открывает Изменить/Скопировать/Отменить. Отмена сохраняет прежний admin guard. Формирование заказа возвращает список и раскрывает созданный заказ без старого модального окна.
- SF06 implemented locally: новый заказ — поставщик и только закреплённые за ним товары. Под названием текущий остаток, справа «Поступит» в базовой единице. Количество95dp/единица120dp/в единице95dp/единица внутри110dp, gap8, вертикальные отступы10dp; на горизонтальном планшете название и поля на одной линии. Поля44/radius10, без стрелок; примечание сворачивается, footer count/Сформировать44. Ввод decimal и текущие stock-конвертации сохраняются. Комментарий до1000символов автоматически сохраняется в optional `note` PurchaseDraft, включая исторический source и экспорт текста; пустой note не меняет прежний JSON/fingerprint, старые копии читаются с пустым note.
- SF07 implemented locally: приёмка — поставщик, накладная/дата в одной строке; название и поля одной строкой на landscape. Из заказа переносятся количество/единицы/упаковки; единственное денежное поле «Сумма строки, BYN», без выбора режима и цены единицы. Под названием цена за базовую шт./кг/л = сумма / фактическое базовое количество,2знака HALF_UP. Сумма остаётся исходной (3шт. за10BYN →3,33 зашт., накладная10,00). Итог и Продолжить позже/Проверить приёмку44, пауза жёлтая. Подтверждение480dp со строками количества, суммой и явным подтверждением превышения; после успешного проведения переход в историю.
- SF08 implemented locally, уточнение владельца12.11: новый черновик получает сумму из текущей себестоимости карточки товара × фактическое количество в базовых единицах. Прежнее правило last supplier receipt заменено прямым указанием владельца. Себестоимость не округляется перед умножением, сумма строки HALF_UP до копейки. Подставленная сумма жёлтая; касание/фокус поля снимает цвет; до проверки всех жёлтых полей приёмка не допускается. До ручного изменения суммы пересчитывается при изменении количества/упаковки. Ручная сумма никогда не заменяется подсказкой, сохранённые черновики не получают молчаливую переоценку. Legacy price-mode переводится в сохранённую сумму; при некорректной старой цене показывается ошибка с сохранением исходного ввода. Склад проводится только существующим подтверждением, повтор/CAS/транзакция прежние.

Локальные цвета всех поверхностей/полей/кнопок задаёт общий MposSupplyTheme, а не существующая другая палитра остальных экранов. Авто-поле имеет amber-контур; shared жёлтая кнопка использует мягкий fill макета, с той же44dp высотой, что зелёная. Редактирование сформированного заказа сохраняет существующее подтверждение Save/Cancel и guard сохранённых версий; строки/поля используют тот же компактный редактор. Это остающаяся безопасная native-форма редактирования, а не изменение команд склада.

Уточнение владельца по скриншоту12.11: отдельная «Приёмка» полностью удалена из верхнего меню. При открытии внутренней страницы приёмки подсвечивается «Поставки»; больше не создаётся автоматически standalone-документ при пустом маршруте. История «Поставок» сохраняет доступ и к прежним standalone-приходам в хронологическом порядке. Их данные и команды не удалены, отдельной кнопки создания без заявки в новом макете нет. Ручная приёмка точного внешнего вида остаётся pending, компиляция и JVM не доказывают пиксельное совпадение.

SF09 implemented locally: вместо `boundsInParent` (координаты вложенной padded Row) Canvas получает ширину вкладки/левую границу из той же геометрии Row: одинаковые трети, gutter28/gap20. Подложка больше не смещается относительно ярлыка и не ждёт измерения предыдущей вкладки. У всех трёх вкладок иконки18dp: поставка/delivery, новый/add, история/history. SF10 implemented locally: поля нового заказа110/130/110/120dp; название занимает1 долю, блок полей2.7 доли и начинается левее, справа «Поступит»92dp. Приёмка: название1 доля/поля3 доли, внутренний порог landscape820dp; общий scroll без растягивающего списка — итог/кнопки непосредственно после строк, не у противоположного края экрана. Количества/деньги/хранение прежние.

SF11 implemented locally: приёмка использует единую сетку из5 равных колонок: принято/единица/в единице/единица внутри/сумма. У неупакованных строк две средние колонки резервируются пустыми, чтобы ширина остальных полей и положение суммы совпадали во всех строках. Высота44dp, подписи16sp line-height и одинаковый gap4dp; dropdown больше не увеличивает высоту до Material48dp. На горизонтальном планшете все поля одной строкой.

SF12 implemented locally: касание поля товара включает позицию с количеством1, если положительное количество ещё не задано; уже введённое положительное количество не меняется. Редактирование упаковки/единицы также включает позицию, ввод количества задаёт её прямо. Вся строка включённых (quantity>0) товаров зелёная; отдельные поля без зелёной заливки. Касание строки переключает включение: исключение задаёт quantity=0, сохраняя упаковку/единицы; повторное включение задаёт quantity=1. Поля перехватывают свои касания для редактирования, без переключения всей строки. Ноль/очистка исключают из сформированного заказа и убирают зелёный цвет. Факты автосохранения сохраняются существующим codec; несколько касаний не дублируют строку. При фокусе числовое значение выделяется для замены, чтобы введённая цифра не дописывалась к автоматически подставленной1. Эти же правила применены к существующему редактору ожидаемого заказа.

## Ручная приёмка

На горизонтальном планшете проверить светлую и тёмную темы, стыки первой и последней активной закладки, долгие названия поставщиков, масштаб шрифта; ввести заказ и переключить вкладки, вернуться без потери ввода; открыть приёмку, изменить количество/упаковки, жёлтую сумму и ручную сумму, перейти через закладку и продолжить сохранённый черновик. Сверить три карточки pending/received/cancelled, недовоз3/10 и превышение12/10, меню⋯ и копирование. Ошибка записи не должна уводить из приёмки. UI-тесты не добавляются; физическое и пиксельное подтверждение выполняет владелец.

Автоматические проверки и фактический результат — `harness/build-log.md`. UI-тесты не добавляются по действующему решению владельца.
