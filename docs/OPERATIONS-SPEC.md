# Операционные области: требования этапов 03–08

Все функции planned. Это детализация уже выбранного объёма; точные финансовые/серверные контракты закрываются до соответствующего кода, а не догадками. Источники: [SOURCE.md](SOURCE.md); правила данных — [DATA.md](DATA.md).

## 03: оплата, история, возврат — S01–S05

Экраны: предварительный итог → выбор наличные/карта/смешанная → ввод принятой суммы/частей → проверка → результат; история → фильтр → детали → возврат. Отметка «карта» фиксирует способ оплаты, сама по себе не подтверждает эквайринг. Реальный платёжный SDK требует отдельного контракта.

| ID | Команда и результат | Отказ/граничный случай |
|---|---|---|
| S01 | CommitSale сохраняет receipt/line snapshots, allocations оплаты/скидки, расход, привязку смены и очищает draft одной transaction | нехватка остатка, stale revision, закрытая смена, ошибка БД: нет продажи/успешного UI/внешних эффектов |
| S02 | commandId уникален; повтор возвращает прежний receiptId | двойной tap/restart после commit создаёт один чек и один расход |
| S03 | RefundReceipt создаёт связанную возвратную операцию по историческому расходу и оплате | повтор/превышение доступного возврата отклонены; новая рецептура не меняет возврат |
| S04 | сумма строк, скидка, доставка, оплата и сдача согласованы по утверждённой decimal policy | некорректная/недостающая split сумма не даёт завершить; доставка не становится товарной скидкой/подарком |
| S05 | история/детали читаются после restart, оплаченный receipt неизменен | повторная печать читает snapshot, изменение каталога не меняет старую цену/название |

До S04 зафиксировать fixtures: валюта/scale, округление строки или итога, распределение скидки по строкам, ограничения скидки, сдача, округление частей, частичный возврат. Подтверждённая часть внешней оплаты не исчезает при закрытии экрана; timeout имеет состояние «результат неизвестен» с проверкой, а не автоматическим повтором списания. Поддержку частичных возвратов включать только с определённой моделью allocations; полный возврат не выдавать за реализованный partial.

После commit печать/Telegram/sync — отдельные задания; их ошибка оставляет receipt успешным с предупреждением и безопасным повтором эффекта. Установка APK блокируется во время commit/recovery; перед installer черновик сохранён. Миграции при обновлении сохраняют историю.

Подробнее поM11/M12: [WAREHOUSE-SPEC.md](WAREHOUSE-SPEC.md). Минимальная сменаM13 входит в03a до sale, см. [MANAGEMENT-REPORTS-SPEC.md](MANAGEMENT-REPORTS-SPEC.md).

## 04: склад, поставщики, закупки — I01–I04

Список остатков открывает движения по товару. Приёмка: поставщик → позиции → единицы/упаковки → количество/закупочная стоимость → preview → подтверждение. Закупка и приёмка — разные документы: заказ поставщику не увеличивает остаток. Получение3из10 закрывает закупку с недопоставкой7 без открытого ожидания; повтор команды не получает товар снова. Редактирование названия поставщика не переписывает snapshot старого документа.

| ID | Приёмка |
|---|---|
| I01 | упаковки переводятся в базовые единицы явно: 2 коробки ×12×0.5 л =12 л; несовместимые единицы/неположительные количества отклоняются |
| I02 | инвентаризация фиксирует baseline revision на товар; любое движение после него, даже продажа+возврат с тем же балансом, требует пересчёта |
| I03 | подтверждённая корректировка — движение; отмена оставшейся инвентаризации не удаляет уже подтверждённые изменения |
| I04 | documentId/commandId защищают приёмку от дубля; при ошибке transaction ни запас, ни документ не изменены; draft восстанавливается |

Средневзвешенная себестоимость подтверждена владельцем2026-10-27:10×2BYN +10шт за40BYN →3BYN/шт; дополнительные расходы поставки требуют отдельного контракта. Приёмка3из10 закрывает заказ с недопоставкой7; получение12из10 требует явного подтверждения превышения. Правка остатка в карточке без причины разрешена: это product_card stock adjustment, а не накладная поставщика; она не увеличивает received закупки и не выдаётся за приёмку. История движений включает причину, время, автора/источник и ссылку на документ.

## 05: смены, сотрудники, права, отчёты — H01–H04

ДеталиM13/M14/M15, cash/report examples и gates: [MANAGEMENT-REPORTS-SPEC.md](MANAGEMENT-REPORTS-SPEC.md).

Смена: выбрать сотрудника, начальные наличные → открыта → операции → сверка/закрытие. H01: повтор close возвращает тот же итог; закрытый период не принимает новую продажу задним числом. H02: разложение продажи/возвраты/наличные/карта/внесения/изъятия сверяется с receipt/movements; формулы ожидаемой кассы и бизнес-день закрепляются fixtures до кода. Отчёт показывает применённый период/зону времени, а не смешивает календарные дни устройства.

H03: матрица разрешений задаёт просмотр, каталог, скидку/ручную цену, возврат, склад, смену, отчёты и настройки. Проверка внутри use case, отказ не оставляет частичных изменений. До появления сотрудников действует явно обозначенный режим владельца; это не постоянная авторизованная admin session. Окончательная матрица ролей/локальная аутентификация остаются открыты до 05.

H04: административная сессия runtime-only и прекращается после restart; PIN/секрет не входит в обычные preferences, backup и logs. Ошибка входа не расширяет права. Экран заблокированной функции объясняет требуемое действие. Удаление сотрудника не удаляет автора исторических операций.

## 06: клиенты, лояльность, зал — C01–C05

ПодробнееM16/M17: [CUSTOMERS-HALL-SPEC.md](CUSTOMERS-HALL-SPEC.md).

C01: поиск клиента текущего заказа по последним четырём цифрам телефона; несколько совпадений показываются отдельными карточками, выбор явный. Неполный ввод/ошибка сети/нет результата — разные состояния. Это подтверждено Web `docs/ORDER_CUSTOMER_PROFILE_RU.md`; payload и device auth утверждаются контрактными fixtures до подключения сервера.

C02: выбор «Использовать подарок» не списывает право немедленно; показывается подходящая строка/причина неприменимости. Allocation относится к конкретным строкам, не поглощает доставку и посторонние товары. Изменение клиента очищает прежние клиентские данные/username и требует пересчёта подарка.

C03: локальный receipt и durable outbox фиксируются до запроса loyalty; retries не создают повторное начисление/списание. Неопределённый server result сохраняется до сверки. Offline-правила серверного подарка уточняются до реализации: не обещать расход удалённого права без проверки.

C04: действия с контактами/согласиями ограничены правами, consent имеет источник/версию/время. Юридический текст не придумывается разработчиком. Telegram-кнопка открывает чат по валидному username после действия пользователя; сама ничего не отправляет.

C05: план зала/стол и бронирование связаны стабильными ID; конфликт пересечения времени явно отклоняется/разрешается выбранной политикой. Изменение брони не дублирует заказ. Не хранить реальные клиентские данные в тестовых fixtures.

## 07: backup и перенос — B01–B05

Поток: системный выбор файла → parse/version/relations → preview количества объектов, конфликтов и фото → подтверждение → staging → atomic activation → результат. Первоначально безопасная замена выбранной базы с резервной копией; merge не включается до утверждения конфликтов ID. Эта политика — предложение до 07, не готовый импорт.

B01: malformed/неполные связи отклоняются до изменения рабочих данных. B02: export→restore синтетического набора сохраняет количества, receipt snapshots и связи. B03: каждый photoId разрешается в staged файл; dangling ссылка не превращается молча в успешный перенос. B04: disk-full/прерывание до активации оставляет прежнюю рабочую базу, restart завершает cleanup/recovery. B05: неизвестная версия даёт понятный отказ, исходный файл сохраняется.

Web v13 — отдельный exchange adapter, не внутренняя схема Room. Admin session/device secrets не импортируются. Экспорт не раскрывает секреты интеграций по умолчанию. До кода нужны обезличенные fixtures каждого поддержанного формата, лимиты архива/фото и решение по финансово незавершённым сессиям. Обычные Room migrations действуют уже с 01 и не ждут backup-этапа.

## 08: оборудование и экспорт — D01–D05

Принтер: адрес/порт, профиль бумаги/кодировка → явный тест → сохранить. D01: adapter проверяется fake transport с timeout/disconnect. D02: повтор печати не повторяет продажу; задания имеют ID/статус, автоматический retry после частичной отправки не гарантирует отсутствие второго бумажного чека и требует показанного пользователю решения. D03: ящик открывается по наличной операции/разрешённой ручной команде, не при каждом рендере.

PDF/XLSX строятся из согласованного report snapshot, экспортируются системным picker/share. Ошибка доступа/пустой отчёт не портит историю. D04: Telegram использует fake endpoint в тестах; реальные сообщения только по настроенному явному действию/авторизованному событию. D05: образцы бумаги, кириллица, итоги, файл на устройстве и ящик подтверждаются на физическом оборудовании. LAN ESC/POS — исходный объём; Bluetooth/USB не считать готовыми.
