Статус: требования для будущей реализации, 2026-10-24. Реализованы только фундамент и обновление APK (00/00.1). Продуктовые функции ниже имеют статус planned. Поведенческий источник — Web commit `1682c88334e6fb13586ce4b530157c59ca062e43`, а не текущий HEAD. Исследование исходников не заменяет запуск и приёмку.

[Каталог и рабочая зона](CATALOG-WORKSPACE-SPEC.md) — подробные сценарии P01–P10/W01–W07 для начала кода. [Остальные области](OPERATIONS-SPEC.md) — требования S/I/H/C/B/D. ## Пользовательский маршрут

1. Установить native APK рядом с Web; пустая база показывает понятный старт, обновление доступно в настройках.
2. В 01 завести категории, простые товары, составы, модификаторы и фотографии; закрыть приложение и убедиться в сохранности.
3. В 02 настроить плитки и папки, собрать заказ, отложить его и вернуться к нему. Расчёт суммы пока предварительный.
4. В 03 провести оплату и возврат, найти чек в истории; результат зафиксирован локально до печати/сети.
5. В 04 управлять закупкой, приёмкой и инвентаризацией. В 05 открыть/закрыть смену, назначить сотрудника и сверить отчёты.
6. В 06 подключить клиентов, согласия, лояльность, столы и бронирования; в 07 перенести поддерживаемый backup с preview.
7. В 08 настроить оборудование/экспорт; в 09 подключить сайт и принимать online заказы. Сетевые сбои не останавливают локальные операции, не требующие сервера.

## Общие состояния и ограничения

Каждый экран различает loading, данные, пустую базу, отсутствие результатов поиска и ошибку чтения. Ошибка записи оставляет введённые поля и даёт повтор; существующий сохранённый объект не заменяется неполным. Ошибка рендера после commit не объявляется отменой уже сохранённой операции.

Планшет: landscape — основной маршрут, portrait/изменение доступной ширины не теряет черновик. Каталог и корзина размещаются рядом при достаточной ширине; при узкой — отдельный переход с видимыми суммой и числом строк. Числа вводятся с десятичной клавиатуры; ошибка у поля, системный размер шрифта не скрывает подтверждение. Минимум 48 dp для основных действий — native требование приёмки, не измерение Web.

Отсутствие сети не мешает каталогу/черновику/локальной продаже. Для серверной лояльности и действий сайта показывается отдельный статус ожидания/отказа. Не выдавать неопределённый внешний результат за подтверждение. Отчёты и журналы используют стабильные ID, даты и явный часовой пояс; правила бизнес-дня уточняются до 05.

## Готовность к коду

Этап начинается с выбранного вертикального сценария и fixtures, затем domain → Room → ViewModel → Compose. Для каждого ID нужны наблюдаемый результат, сценарий ошибки и доказательство в build-log. Подробная документация не переводит planned в implemented. Сборку/публикацию выполняем только при изменении кода соответствующего этапа; для этой документационной итерации новый APK не требуется.
