## Почему два инкремента

Текущие repositories держат долгоживущие ViewModels/Room readers, administrative writes используют adminTransaction, финансовые writers — InstallationGate; часть initialize/cleanup входит напрямую в Room transaction. Один общий installer mutex не доказывает exclusive restore для всех consumers/writers. До применения нужен отдельный durable maintenance/activation protocol и generation fencing, который охватит эти пути. Не заменять live db-файл за спиной открытого Room и не объявлять несколько rename атомарными.07.3a вообще не пишет в рабочие таблицы/активные фото.

## Logical fingerprint v1

Отдельный от ZIP/file SHA-256 fingerprint всех17business tables+Room identity, sorted table/column/row traversal, type tags+length-prefixed UTF-8/BLOB и exact64bit INTEGER/NULL; затем sorted photo IDs+photo SHA. FLOAT отвергается;≤2Mrows. android_metadata/locale, SQLite page layout и archive timestamp не входят. Разная ZIP упаковка/VACUUM/createdAt при прежних данных не создаёт ложный target conflict; любое изменение payload/revision/command/stock/photo меняет fingerprint. Он выявляет изменение снимка, не является подписью/паролем/глобальным write fence.07.3b обязан перепроверить target в exclusive maintenance и заново показать preview при изменении.
