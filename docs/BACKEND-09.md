## Найденный контракт

| Действие | HTTP | Значимое поведение |
|---|---|---|
| Связь | GET /health | `{ok:true}` ещё не означает принятие ключа |
| Проверка ключа | GET /api/operational/state | `available/fresh/state`; `state:null` допустимо для нового устройства |
| Меню | POST /api/menu/sync | X-Device-Key; deviceName/categories/products; регистрирует ключ, активирует устройство; отсутствующие товары деактивирует во **всём** каталоге сервера |
| Фото | POST /api/media/upload | productId/dataUrl, JPEG/PNG/WebP ≤1,5 MB; только зарегистрированный ключ; URL с версией содержимого |
| Тарифы | GET + PUT /api/device/delivery-tariffs | publicationId/baseVersion/tariffs, optimistic concurrency; ключ должен совпадать с серверным DELIVERY_TARIFF_DEVICE_KEY |
| Доступность | POST /api/availability/snapshot | version1/revision/sampledAt/items/settledWebOrderIds |
| События | GET /api/orders/events | SSE; backend принимает X-Device-Key в header, поэтому native не передаёт секрет в query; snapshot последних20 новых заказов, повтор каждые2сек; replay cursor отсутствует |
| Принятие | POST /api/orders/{id}/accept | повтор accepted идемпотентен; readyEstimate текущий сервер игнорирует |
| Готовность | PATCH /api/orders/{id}/status | текущий backend принимает status=ready; маршрута POST /ready, вызываемого Web, нет |

Ключ устройства не разделяет организации. Серверные БД/каталог/заказы общие внутри deployment. PUBLIC_BASE_URL для фото и DELIVERY_TARIFF_DEVICE_KEY настраиваются при развёртывании сервера; клиент не может изменить env вводом URL.

## Реализованные части (local implemented; device/staging pending)

1. **09a / N01.CFG**: редактируемые URL, имя/ключ, пути API и timeout. Keystore/AES-GCM, AtomicFile, noBackupFilesDir, revision и admin generation. Сохранение отдельно от GET health/state/SSE probe; без создания заказов, redirect и скрытых HTTP retry.
2. **09b / N04.PUB**: preview категорий/товаров/фото/тарифов и подтверждение полной публикации. Сохраняются исходные external IDs импортированных товаров. Фото отправляются по одному; обновление меню с подтверждёнными URL отдельным шагом. Частичный успех не скрывается. Тарифы имеют durable publicationId/baseVersion: потерянный ответ повторяется тем же ID; конфликт требует нового preview версии. Availability/revision сохраняется перед запросом и считается успешной только при applied=true. В карточке товара подключены описание и два online-флага (ProductDetails v3, старые v1/v2 читаются). Сохранение товара само меню не публикует.
3. **09c / N02.INBOX**: bounded SSE parser, header auth, reconnect/backoff/jitter и server sleep retry. Канал привязан к STARTED lifecycle; отмена закрывает Call. Inbox зашифрован отдельно для target+dataset, одинаковые snapshots не переписываются и не перерисовывают UI. Backend даёт окно последних20 новых заказов: по мере принятия из него приходят следующие. Это не replay cursor и не гарантированная полная история серверных изменений.
4. **09d / N03.ACCEPT**: модальные События поверх рабочей зоны → preview/локальное ETA → atomic parked+accept intent → HTTP ACK. Детерминированный session ID и отдельный indexed document не дают создать копию. Серверный product ID авторитетен, fallback имени только для legacy без ID. Проверяются сумма, количества, рецептура/резервы/доставка. Пока сервер не подтвердил принятие, checkout/частичные оплаты/продажа блокируются.
5. **09e / N03.READY**: локальная готовность+очередь → PATCH status=ready; допускается после оплаты через События. Оплата — стандартная кассовая транзакция, paid marker коммитится с receipt; settlement availability после оплаты, партиями до100 ID. Отмена — durable intent, блокировка оплаты, PATCH cancelled, затем удаление локальной корзины/резерва; оплаченный чек отменяется через обычный возврат. Печать кухни запускается после local commit с существующими print claims.
6. **09f / N05/N06**: задачи привязаны к URL/key/orders route и поколению данных. После restore требуется явное сохранение подключения; переназначаются только локально существующие заказы того же target, чужие задания не отправляются на новый сервер. Native validator понимает online documents и quotedPrice, проверяет связи с корзиной/receipt. Финансовая история не сканируется для каждого события: per-session lookup, отдельная SQL-выборка активных задач, online ACK revisions исключены из наблюдения рабочей зоны. Адресные JVM tests выполнены; instrumented/реальный сервер — отдельная приёмка.

## Решения владельца 09.11

- Отдельные backend+БД для каждой организации.
- Онлайн-заказы подключаем сейчас; лояльность остаётся TODO.
- Цена сайта10 при новой цене POS12 сохраняется10, в том числе после обновления рецептуры/каталога. Обычное добавление товара на кассе по12 не сливается с online-строкой.
- Товары с обязательными модификаторами не публикуются: сервер не передаёт выбор.
- **Backend не менять.** ETA хранится только на планшете. Готовность отправляется существующим PATCH /status, без несуществующего POST /ready.

## Подключение нового магазина

1. Развернуть совместимый M-POS backend с отдельной БД. Настроить HTTPS/PUBLIC_BASE_URL и DELIVERY_TARIFF_DEVICE_KEY на сервере.
2. В admin → Сетевые конфигурации → Меню и backend ввести URL, имя и ключ, сохранить. Ключ скрыт по умолчанию. Дополнительные маршруты позволяют работать за reverse proxy; JSON-протокол при этом должен оставаться совместимым.
3. Проверить связь: как в Web, это только GET /health. Затем отдельно проверить канал заказов: GET /api/orders/events с ключом в заголовке. Успешный health не означает принятие ключа. Operational state больше не является условием проверки связи. Отказ канала401/403 показывается с точным HTTP-кодом; каталог ради диагностики не публикуется.
4. Синхронизировать → проверить адрес, количества и предупреждение полной замены → Опубликовать. Проверить итог всех частей, особенно тарифов/фото. Пустой каталог скроет всё меню.
5. Включить получение онлайн-заказов и сохранить. При активном приложении идут SSE, heartbeat/overload и обновления остатков. Обычная локальная касса работает без сети.

## Переход с Web

Сначала завершить уже принятые в Web онлайн-заказы и отключить старое приложение от канала. В native восстановить каталог/составы/сотрудников/рабочую зону, использовать **прежний ключ устройства** для того же backend (в частности, источник тарифов останется тем же), проверить preview и синхронизировать, затем включить получение заказов. Для другой организации нужны её собственные URL/key/БД.

Текущий сервер не владеет атомарным назначением заказа конкретному планшету: повтор accept для accepted возвращает успех любому устройству. Поэтому два одновременно принимающих POS могут взять один заказ. Без серверной доработки поддерживаем один активный принимающий POS на deployment. Код сервера не изменён.

## Ограничения и остающаяся приёмка

- Категорийные online-флаги из Web сохраняют приоритет над товарными; редактирование этих флагов в native окне категорий пока TODO. Новые native категории доступны по умолчанию.
- Сетевой контекст уже принятых Web-заказов через backup остаётся прежним TODO (onlineOrderCompletionPending); завершить их в Web до миграции. Это не меняет перенос реализованных обычных открытых чеков/частичных оплат.
- Объединение online-чека с другим чеком пока блокируется: иначе теряется связь server ID с единственной локальной оплатой. Обычные чеки объединяются как прежде.
- Backend Telegram-команды владельца, серверные online-уведомления/лояльность не активированы этим этапом; прямые Telegram-отчёты native работают отдельно.
- Новые тесты storage/Room/publication compile-only до запуска Android16. Подготовлены проверки rollback/idempotency/цены/оплаты/cancel/потерянного ACK тарифов/version conflict. Реальная публикация, сетевые сбои планшета, перезапуск с pending, restore/rebind и staging walkthrough ещё не подтверждены.
