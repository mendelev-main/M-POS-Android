Уже готовый заказ показывает ✓Готов. Paid и ready независимы; принятие печатает кухню один раз, оплата списывает товары/кассу один раз.

6. LO02: клиент заказа, server profile/согласие, подарок с доступным балансом. Смена клиента очищает выбор, ошибка сервера не становится нулевым балансом.
7. LO03: adapter android-loyalty-pricing.js — один самый дешёвый подходящий товар за программу, без повторного использования единицы и без бесплатной доставки. Денежный расчёт остаётся decimal/копейки и историческим снимком native.
8. LO04: перед подарком серверная перепроверка участия/баланса. Сбой позволяет явную оплату без подарка. Продажа/возврат сохраняют durable effects в той же локальной транзакции; HTTP потом, replay по исходному orderId. Подключение/target/dataset не смешиваются между организациями и восстановленными базами.
9. ON05/LO05: адресные JVM/Room/UI fixtures, compile и ручная приёмка владельцем; реальные заказы/Telegram/печать не используем для автотестов.

## Реализованный путь

События → заказ → время → durable запись в Отложенных → accept. Приём не вытесняет текущий чек. «Готов» доступен в Отложенных и текущем заказе; повтор подтверждения использует исходный заказ. Отмена из Отложенных идёт через сервер. Старый PATCH вместо ready удалён, запасного silent-статуса нет. Имя/контакт клиента сайта сохраняются; профиль лояльности загружается при наличии customer_id, перед оплатой обновляется. Backend не изменялся.

Панель администратора → Лояльность: программы/клиенты, создание/редактирование/активность/удаление, поиск и обе группы товаров. Клиент заказа: поиск последних4 цифр, явный выбор, создание, профиль, согласие с актуальным документом сервера. Согласие требует открытой смены и реального сотрудника. Корректировка баланса — с причиной, ожидаемым балансом и requestId. Доказательство администратора берётся из успешного входа, только в памяти текущего процесса, очищается при выходе.

Подарки распределяются по самым дешёвым подходящим целым единицам; единица используется только одной программой. Сохраняем принятое native-правило HALF_UP по строкам: сначала цена оставшихся платных единиц, разница — подарок. Это явное отличие от глобального JS-округления subtotal: при дробных остатках/скидках копейки между строками не перераспределяем. Доставка остаётся платной. Перед подарком свежий профиль и сверка consent/balance/правил; при сбое можно явно продолжить без подарка, без автоматического списания.

Начисление и возврат — документы loyalty-pending/result внутри финансовой транзакции. Никакой HTTP до commit. Ограниченная очередь10, исходные orderId/occurredAt/customer/consent/items, отдельный backoff. При потере ACK replay того же запроса; возврат до отправки проходит после исходной продажи. HTTP400/409 становится «требуется проверка», не ложным успехом. История чека и печать показывают подтверждённый прогресс либо ожидание/ошибку. Restore валидирует связи эффектов и чеков; продолжение того же подключения требует явного подтверждения backend после восстановления. На другой URL/ключ операции не отправляются.

На уровне OnlineOrderDeletion повторно проверяются active/generation; внутри общего operation mutex проверяются backend target/dataset, статус new и отсутствие локального принятого record. Физический DELETE в прочитанном M-Pos-Backend/server.js отсутствует. Используется существующий PATCH {ordersPath}/{id}/status с единственным полем status=cancelled. Этот handler в исходнике только обновляет SQL и возвращает ok/order; Telegram/accept/ready/печать не вызываются. Это логическое удаление из новых заказов, серверная запись сохраняется, в клиентской истории может остаться статус отмены. Backend не меняли/не публиковали. Текущий deployed handler/внешние DB triggers не проверялись реальной записью: рабочие заказы ради теста не удаляем.

Локальное удаление только после ok + совпадающих id/status=cancelled. При ошибке/неоднозначном ответе окно остаётся с сообщением, нет скрытого fallback. Повтор PATCH cancelled идемпотентен по состоянию. Удаление не создаёт native чек, расход склада, оплату, kitchen print или Telegram effects. Tombstone в encrypted inbox2 не даёт старому new SSE воскресить заказ после restart; inbox1 читается. Поздний accept того же ID локально отклоняется. После успеха возвращаем список событий, без success banner или сообщения клиенту.

Ограничения существующего API: PATCH status не имеет CAS/expected status, поэтому одновременная обработка одного заказа другим POS не защищена серверной транзакцией сравнения. Действует ранее закреплённая схема одного активного принимающего POS на deployment. Серверный SSE отдаёт последние20 новых, поэтому отсутствие ID само по себе не трактуется как глобальное удаление старого кеша другого native POS. Добавление server CAS/delete — отдельная доработка backend, в эту задачу не входит.
