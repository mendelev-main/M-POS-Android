## 03b.1 — денежное ядро

SaleMoney не зависит от Android/Compose/Room и не пишет финансовую операцию. Вход: стабильные line IDs, unitPrice≤2 decimal, qty≤9, одна percent/fixed скидка с snapshot названия; тип заказа и explicit DeliveryCharge(id/name/feeMinor/revision), подготовленные PaymentInput(method/amountMinor/givenMinor). delivery требует тариф, включая выбранный бесплатный тариф0; here/takeaway отвергают скрытый fee.

Вычисления BigDecimal до границы net line HALF_UP2→Long minor. Quote хранит rounded gross/discount/net каждой строки и checked totals. discountMinor=grossMinor−netMinor, а не самостоятельно округлённая скидка с повторным вычитанием. Процент — точный decimal shift на2 разряда: Kotlin BigDecimal operator / не используется, поскольку его scale может преждевременно округлить дробную скидку. Input/string/list limits, duplicate IDs, invalid method/given/sum и Long overflow дают отказ.

PaymentAllocation cashGiven/change сохраняются отдельно от cash net. ExpectedCashAfter=current expectedCash+cash net−deliveryCashOut; card не даёт наличных для курьера. Ровно один cash-out доставки; эта сумма не вычитается из оплаты чека. При shortage cash выдачи отказ. EqualSplit2–10 сохраняет каждую копейку; нулевые части допустимы, карта никогда не содержит given/change. Это расчёт подготовленных частей, не интеграция банковского списания и не durable подтверждение отдельных частей.

Примеры/tests:0.05×3−10%=0.135→0.14;3different lines0.045→0.05 each,total0.15;fixed1×2 →18+delivery5=23;cash40/card60/given50→change10/cash+40;card25/delivery5 needs cash5;10/3→3.34+3.33+3.33;0.01/3→0.01+0+0;overflow/malformed/refusal. Производные quote/payment DTO никогда не являются доверенным разрешением записи: future repository повторяет расчёт из committed snapshot внутри transaction.

### 03b.3b.1 — редактор распределения (чистый домен)

`SplitEditor` строит кандидата оплаты со стабильными ID частей в пределах checkout. ID не является номером строки: при изменении количества оплаченные части переходят в начало, но сохраняют ID, сумму, способ, внесённые наличные и признак подтверждения. `nextId` монотонен; удалённый ID не используется вновь. Будущий persisted формат обязан сохранять этот счётчик вместе с частями. Редактор не подтверждает оплату и не пишет Room; paid-флаги принимает только будущая транзакционная интеграция из сохранённого прогресса.

Распределение соответствует pinned `payment.js`177–270: 2–10 частей, остаток копеек первым; при изменении количества остаток после подтверждённых частей распределяется между неоплаченными. Удаляются последние неоплаченные части. Нельзя удалить подтверждённую часть или оставить положительный остаток без неоплаченной части. При прежнем количестве действие ничего не меняет.

При вводе суммы сохраняются подтверждённые и предшествующие неоплаченные части; последующие получают остаток поровну. Запрос выше доступного остатка ограничивается остатком, как в Web. При редактировании последней неоплаченной части разница распределяется между предшествующими неоплаченными. Пример: 3,34 + подтверждённые 3,33 + 3,33 BYN; ввод 1 BYN в последнюю даёт 5,67 + 3,33 + 1 BYN. Единственная неоплаченная часть всегда равна оставшейся сумме: ввод 0 не может превратить чек в недоплату. Это намеренное исправление Web, где одиночный остаток может перестать совпадать с итогом.

Смена способа оплаты очищает внесённые наличные; изменение/перераспределение суммы очищает их у затронутых неоплаченных частей, чтобы старая сдача не переживала пересчёт. Для наличных можно очистить ввод, но введённая сумма не меньше суммы части. У карты наличный ввод запрещён. Нули допустимы; отрицательные суммы, неизвестные/повторные ID, несовпадение итога и переполнение отвергаются. Подтверждённые строки нельзя редактировать даже тем же значением через команды редактора.

Граница этой подчасти: только S04 pure allocation и ID lifecycle. CheckoutCodec1, split-progress1, schema7, действующий UI и API подтверждения остаются прежними. **Редактирование сохранённых частичных оплат пока недоступно.** Следующая 03b.3b.2 должна атомарно связать редактор с progress/checkout/result/audit и сохранить replay старых команд. Нельзя просто заменить индексы ID: прежний fingerprint подтверждения включает всю матрицу и revision. Нужны совместимое чтение старого progress1, сохранение доказательств уже принятых команд, optimistic revision, rollback/concurrent edit-confirm/reopen/replay-after-edit/final тесты. После этого — общий UI отдельных подтверждений и показ pendingCash, затем проверка активного progress при APK replacement.

### 03b.3b.2 — транзакционное редактирование прогресса

`SplitPaymentRepository.edit` принимает стабильный commandId, исходный SavedCheckout, ожидаемую revision прогресса и одну типизированную команду Count/Amount/Method/Given. Paid-флаги/ID берутся из БД, а не из запроса UI. Команда сохраняет checkout с новой revision, progress2, operation result и audit одной транзакцией под InstallationGate. Корзина, скидки, тариф, смена и владелец остаются исходными; повторно проверяются актуальность ссылок, резерв/остатки, сумма и выдача доставки. Неполный ввод наличных у неоплаченных частей может храниться как null; это не подтверждение и не основание для финальной продажи.

Progress2 хранит прежние confirmed indices вместе с ordered `partIds` и `nextPartId`; пары indices/IDs меняются только редактором. Room schema7/checkout1/receipt1 остаются прежними. Progress1 читается без изменения; первая новая команда переводит его в2 атомарно. Для каждого прежнего подтверждения проверяется существующий operation_result и создаётся stable-ID alias, указывающий на тот же результат. Старый ключ и его fingerprint остаются неизменными.

Новый `confirmPart` получает ID и снимок именно подтверждаемой части. Ключ зависит от checkout commandId и part ID, fingerprint — от неизменяемого контекста заказа и payment(method/amount/given); revision checkout и остальные неоплаченные части в него не входят. Поэтому повтор после перестановки строк, редактирования и final commit возвращает тот же результат, а изменение суммы/способа/внесённых наличных/владельца даёт конфликт. Старый index API после перехода в2 разрешает только replay уже записанных старых команд; новых подтверждений по позиции не создаёт. Для подтверждения cash требуется реальный сохранённый given; null разрешён только в неоплаченных строках. Финальная Sale по-прежнему требует все части paid и списывает склад/кассу ровно один раз.

Сначала result lookup, затем проверка revision; повтор успешной edit-команды возвращает её ID, не применяя перераспределение снова и не подменяя текущий progress старым снимком. UI должен загрузить текущее состояние после результата. Разные конкурирующие edit/confirm с одной revision имеют одного победителя. Удалённые ID не используются повторно. После complete новые edit запрещены; доступен только final Sale. Consumption оставляет прежний монотонный completed tombstone, результаты подтверждений сохраняются отдельно.

### 03b.3c — интерфейс отдельных подтверждений

В режиме «Разделить / смешанная» равные части заполняют только суммы, без выдуманного received cash. «Начать оплату по частям» вызывает отдельный saveSplit: сумма частей должна совпасть с quote, тариф/смена/ссылки/наличные доставки проверяются, nullable given разрешён только как неоплаченный ввод. Обычный save/финальный SaleMoney.payments сохраняют строгую проверку. Сохранённый multi-part checkout открывается в новом экране, в том числе старый подготовленный split.

На экране показаны общий итог, подтверждённая сумма, остаток, pendingCash и касса по завершённым чекам отдельно. Карточки используют общие Surface/MposSelect/MposButton/MposDialog/Field/Close. Неоплаченные части редактируются отдельными окнами суммы/наличных/количества; смена метода сохраняется сразу. Наличные без given не подтверждаются; карта требует явного подтверждения ручной оплаты на терминале, SDK не подключён. Нулевые части можно подтвердить. До первого подтверждения можно отказаться от split и вернуться к подготовке; IDs тогда предварительные, без operation results. Изменение исходного checkout до первого подтверждения может перенумеровать предварительные строки. После первого подтверждения действуют сохранённые stable IDs/nextId, paid snapshots, transactional editor и guards03b.3b.2.

После first paid экран не разрешает Back/History/редактирование корзины, скидок и тарифа. Подтверждённая строка показывает сумму/given/change и отключённые действия; прочие части доступны для редактирования. Состояние читается одной Room transaction, новый ViewModel восстанавливает прогресс и complete. После последней части появляется «Завершить продажу» с прежним общим confirmation preview. Это явный завершающий шаг native вместо Web setTimeout auto-finalize: если final commit не выполнен, complete progress остаётся восстанавливаемым, склад/касса ещё не проведены. Финальный чек всё равно один; повтор использует тот же checkout commandId.

При ошибке split write ViewModel сначала читает фактически сохранённое состояние и не рисует оптимистичное «Оплачено». Если не удалось и это чтение, новые действия/уход блокируются до успешного повторного чтения; не создаётся новый checkout для обхода неизвестного результата. Финальная продажа использует прежний outcome recovery. Поля ещё не подтверждённого открытого окна не обещаются сохранёнными при cold restart.
