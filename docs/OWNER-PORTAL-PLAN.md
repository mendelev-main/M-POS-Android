# Страница руководителя и будущий кабинет

Запрос владельца11.11.2026. Сейчас implemented locally: в панели администратора стандартная карточка «Управление», открывающая страницу «Руководитель». Телефон, почта, Telegram ID собственника доступны сразу; плюс добавляет аналогичные поля администраторов. Одна кнопка сохраняет весь справочник атомарно с revision/generation guards; данные прежнего management.contacts.v1 сохранены. Выход без сохранения не записывает правки. Справочник контактов не назначает employee/admin роли.

Будущий кабинет на сайте — TODO, сервер и сайт в этой задаче не меняются.

## Цель
Владелец входит в кабинет своей организации и видит число участников акций, их согласованную клиентскую базу, активные/доступные награды, прогресс и полезную агрегированную статистику. Ранее принятое разделение: отдельные backend и база на организацию; приложение настраивается URL/ключом.

## Зависимости и порядок
1. Серверная учётная запись руководителя со стабильным account ID и привязкой к конкретной организации/backend. Подтверждённый контакт/механизм входа согласовать перед реализацией; локальные phone/email/Telegram ID не являются доказательством права доступа.
2. API регистрации/проверки связи account↔organization, профиль руководителя и делегированные администраторы с явными правами. Device API key и пароль локальной админ-сессии остаются отдельными.
3. Авторизованные API чтения данных лояльности: число зарегистрированных и отдельно активных участников, consent/status, пагинируемые поиск/карточки клиентов, программы/прогресс/награды. Источник правды — backend; локальный справочник не подменяет его.
4. Интерфейс кабинета: обзор показателей, участники/поиск, карточка участника, фильтры программ/статусов. Периоды, трактовку «зарегистрирован в акции» и дополнительные метрики уточнить на примерах.
5. Интеграция страницы руководителя native с серверным профилем: явная привязка, проверяемое сохранение и состояния offline/conflict/revoked access. До этого контакты только локальные.
6. Проверки разграничения двух организаций, отзыва доступа, неполных/устаревших ответов, больших клиентских баз, пагинации и consent boundary.

Готовность будущего кабинета: подтверждённый руководитель видит только данные своей организации, счётчики согласуются с пагинируемой базой, logout/revoke закрывает доступ. Текущая форма контактов эти критерии не закрывает.

## Верхнее меню
Щит при активной сессии → settingsAdmin (корень панели); шестерёнка → settings (корень настроек), включая повторный клик из внутреннего раздела; M POS → workspace с корнем раскладки, текущий заказ остаётся в VM/базе. Новый navigation request сбрасывает локальную вложенную страницу даже при прежнем route, runtime admin session сохраняется. Во время незавершённой атомарной операции остаются существующие guards. В карточке товара верхнее меню теперь отображается; черновик не удаляется при переходе. Прочие модальные окна используют стандартную модальность.
