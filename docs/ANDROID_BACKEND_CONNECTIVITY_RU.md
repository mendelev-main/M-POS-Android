# Android: backend и Telegram — 08.10.2026

Владелец подтверждает, что сайт и работающий бот исправны, но сетевые проверки на Android показывают отсутствие связи. Также подтверждено обновление новых подписанных APK.

## Проверенные факты

- Публичный HTTPS /health настроенного по умолчанию backend project-dubrovno.up.railway.app отвечает 200 и ok:true. Это проверка доступности сервиса, не авторизации конкретного планшета.
- В текущем M-Pos-Backend/server.js и ready-server.js нет маршрута POST /api/orders/test. Android и прежний iPad вызывают его. HTTP 404 этой кнопки не доказывает отсутствие сети.
- Backend принимает поток /api/orders/events, Telegram-настройки и ответы статистики только с активным devices.device_key. Устройство регистрируется существующей ручной /api/menu/sync. Проверка /health не регистрирует устройство.
- Android ранее использовал Kotlin для каталога и SSE, но /health, тест заказа, PUT Telegram-настроек и POST статистики владельца оставались fetch в WebView. Сам по себе этот факт ещё не доказывает, что конкретный отказ пользователя вызван CORS.
- Native SSE закрывается при 401. После первой ручной регистрации через каталог поток не перезапускался, поэтому заказы/запросы владельца могли оставаться недоступными до нового старта.
- Прежний TelegramClient скрывал HTTP причину отказа одним общим сообщением. Рабочий бот на сервере не означает, что сохранённый на Android token/chat/topic актуален или что с планшета доступен api.telegram.org.

## Изменения Android

MPosBackendHttp выполняет перечисленные запросы через OkHttp: ограниченный список маршрутов, только HTTPS, запрет credential URL, ограничение времени, без redirect и автоматического повторения. health не передаёт ключ; другие маршруты передают X-Device-Key. Проба SSE проверяет статус и Content-Type и сразу закрывает временный поток, не читая бесконечное тело. Настоящий поток остаётся в MPosWebSse.

«Проверить и сохранить» проверяет /health и принятие deviceKey потоком. 401 предлагает ручную синхронизацию меню. После успешной явной проверки или ручной синхронизации поток перезапускается. Автоматической передачи каталога нет; availability retry policy не изменена.

Тестовый заказ сохраняет свой маршрут, но 404 теперь обозначает отсутствующий endpoint; 401 — незарегистрированный ключ. Не подменять успешный заказ фиктивным локальным событием.

Telegram показывает безопасные различия: отклонённый токен, недоступный чат, тема, запрет отправки, rate limit, DNS, TLS или timeout. Произвольный ответ Telegram и URL с токеном не показываются. HTTP соединение sendMessage закрывается в finally.

Сервер и процесс бота не изменены, второго Telegram poller нет. Схема Supabase не изменена; закрытые ключи и рабочие credentials не читались. Настройки backend/bot production и доступ конкретного планшета этим срезом не подтверждены.

## Проверка и оставшийся объём

Добавлены JS/JVM проверки native route/method/header dispatch, timeout/cancel, SSE probe без чтения тела, HTTP 401/404, перезапуск после успешной ручной синхронизации и безопасные Telegram ошибки. По решению владельца локально тесты/lint/APK не запускались: их выполняет Actions. Проверка git diff --check выполнена.

Физические случаи pending: новая сборка → «Проверить и сохранить»; при 401 ручная синхронизация меню; повторная проверка, реальный заказ сайта → Android; сохранение Telegram-настроек → запрос статистики владельца; Telegram test с корректными/неверными token/chat/topic; отсутствие интернета и закрытие формы во время проверки. Не создавать реальные тестовые сообщения или заказы автоматически от агента.
