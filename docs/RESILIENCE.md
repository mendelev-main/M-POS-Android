# Сохранность данных, восстановление и миграции

Статус: общий контракт сохранности; Room7 и atomic sale/history repository уже проверены CI03b.2b (SALE-03B). Backup/outbox для будущих адаптеров и полный recovery UI реализуются по своим этапам. Web `android-safety.js` использует journal roll-forward поверх localStorage; native сохраняет атомарность через Room transaction и не переносит Web journal буквально. Источник наблюдения: [SOURCE.md](SOURCE.md), pinned commit, `docs/STORAGE_WRITE_BOUNDARY_RU.md` в Web.

## Порядок локальной команды

1. Создать стабильный commandId до начала операции; сохранить/восстановить его вместе с намерением, если результат может потеряться при restart.
2. Проверить формат, права и предварительные зависимости вне короткой transaction; не запускать HTTP/печать.
3. В transaction найти прежний OperationResult, проверить fingerprint/актуальные revisions, выполнить изменения и сохранить result/outbox.
4. После подтверждённого commit опубликовать результат UI и разрешить обработку внешних эффектов.
5. Если ответ потерян или outcome неоднозначен, прочитать результат по commandId. При достоверном rollback показать отказ без ложного успеха.

Для денежных/складских операций commandId нельзя забывать по таймеру, если повтор может прийти после restart/восстановления; срок хранения и backup scope определяются вместе с историей. Повтор с другим payload всегда конфликт. Обычный double tap не оправдывает два разных commandId одного намерения.

## Сбои по границам

| Момент | Сохраняемое состояние | Действие после возврата/старта |
|---|---|---|
| валидация/до записи | прежние committed данные | восстановить форму/ошибку, безопасный повтор |
| БД откатила transaction | без частичной продажи/резерва | StorageFailure, поля остаются |
| процесс умер во время transaction | результат определяет БД после открытия | lookup commandId, не считать по отсутствию UI |
| commit выполнен, UI не получил ответ | receipt/result существуют | показать существующий результат |
| внешний HTTP принят, ответ потерян | эффект InFlight/неопределён | reconciliation/idempotent retry по контракту |
| печать частично отправлена | бумажный результат неизвестен | предупредить; явная повторная печать, без второй продажи |
| мало места при фото/backup | прежний активный dataset | очистить только staging, не исходные файлы |
| ошибка схемы/целостности | данные не заменяются пустой базой | RecoveryRequired и безопасные действия |

Не всякий IOException означает повреждение БД. Busy/Conflict/DiskFull/InvalidSchema/Corruption/Cancelled должны различаться для диагностики и допустимого повтора. Не переключать всё приложение навсегда в «сломано» из-за ожидаемого revision conflict. Нельзя автоматически удалять БД для устранения ошибки.

## Фото: подготовка → ссылка → уборка

Скопировать picker stream в private staging, проверить лимиты/формат, закрыть запись; подготовить immutable файл с новым photoId в активном каталоге. Затем transaction меняет PhotoRef/Product. Отказ БД оставляет orphan файл без активной ссылки, который можно убрать позже. Старое фото удаляется только после успешного commit и проверки всех ссылок.

Нельзя сначала записать ссылку на ещё не готовый файл или сначала удалить старое фото. Сбой cleanup не отменяет сохранённую карточку. Cleanup работает по собственному namespace, не по произвольному пути из backup; при гонке с reader/новой ссылкой удаление откладывается. Fault tests прерывают каждый шаг, а не только симулируют отказ picker.

## Room schema и APK update

Каждая выпущенная схема имеет сохранённый schema artifact и миграционный путь из всех поддерживаемых прежних версий. destructive fallback для рабочих данных запрещён. APK versionCode не используется как номер Room schema. Migration не выполняет HTTP, не меняет исторические суммы по текущей рецептуре и не оставляет параллельно работающий repository старой схемы.

Тесты миграции проверяют данные и инварианты, а не только успешное открытие: decimal, ссылки, command results, receipt snapshots, движения, current/parked, outbox binding. Повторное открытие не применяет изменение второй раз. Переход bootstrap→Room сохраняет updater markers/preferences и не сбрасывает канал.

Если старая база требует неподдержанного пути или создана более новой версией, показать отказ с сохранением файла; не делать downgrade данных. Установка старого APK не считается стратегией rollback после миграции. План восстановления использует совместимый backup и версию приложения с поддержанным schema/format.

В 03 installer guard координируется со всеми writers, import/recovery и отправителями несовместимых эффектов. Перед запуском installer подтверждается сохранение draft. В 00.1 такого предметного guard ещё нет, поскольку нет бизнес-операций.

## Import/restore отдельным протоколом

Этап 07 должен реализовать явный activation protocol: validation/preview → staging database+photos → exclusive maintenance → checkpoint prepared → activation → проверка открытия/ссылок → release maintenance → отложенный cleanup прежнего dataset. Внутри одной БД обычная transaction возможна; замена набора БД+фото требует отдельного durable activation marker и определённого восстановления при каждом шаге.

Точный механизм переключения/сохранения marker фиксируется до кода с fault fixtures. Нельзя обещать атомарность Room и файлов одним `rename` нескольких путей. Старый dataset не уничтожается до проверки новой активации; временный prepared набор не должен автоматически становиться активным из-за одного наличия каталога. Рабочие consumers получают согласованную generation и не смешивают новую БД со старыми photos/cache.

Внешние эффекты из восстановленного backup не отправляются автоматически: это может повторить уже выполненные печать/loyalty/WEB действия. Они переводятся в нуждающийся в сверке статус по контракту restore. Идентичность команд/операций сохраняется; активные admin sessions/секреты привязки не импортируются. Актуальный endpoint не назначается старому outbox молча.

## Outbox и фоновые повторы

Local commit гарантирует наличие задания, а не exactly-once внешний эффект. Worker берёт запись с lease/token, фиксирует попытку, выполняет transport и сохраняет outcome только если всё ещё владеет попыткой. Lease восстанавливается после смерти процесса; его истечение само по себе не доказывает, что сервер не выполнил запрос.

| Тип эффекта | Безопасная политика |
|---|---|
| API с подтверждённым idempotency key | retry тем же ключом/payload, затем сверка результата |
| API с чтением результата, без доказанной повторяемости mutation | сначала reconcile; повтор только по контракту |
| принтер/ящик, неизвестный факт отправки | не слепой auto retry, явный статус/ручное действие |
| публикация availability/menu version | дедупликация/замена устаревшего snapshot только по согласованному server contract |

Retry/backoff имеет пределы нагрузки и видимый статус, auth/validation не маскируются сетевым ожиданием. Один coordinator/unique worker и transaction lease предотвращают параллельную отправку одной записи. Смена часов устройства не должна навсегда заблокировать lease/retry; стратегия clock и восстановление после reboot проверяются отдельно.
