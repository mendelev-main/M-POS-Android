## План и acceptance

Последовательно: исторические DTO и точная агрегация → существующая read transaction → основной экран → регрессии → проверки. Основа: приложенное владельцем M-POS-Analytics-Spec-Codex.md v1.0; новые требования заменяют прежний AA02 с тремя колонками.

- AN01: общий период включительно, presets/произвольные даты, refresh; прежний ReportViewModel сохраняет фильтры, очищает старый snapshot, отменяет устаревший запрос и закрывает данные при logout.
- AN02: шесть KPI: продажи/возвраты/выручка/чеки/возвраты-операции/средний чек.
- AN03: чистая историческая себестоимость; валовая прибыль = выручка − себестоимость. Прежний details.profit с курьерскими расходами сохранён для совместимости. Рентабельность при нуле — прочерк.
- AN04: чистые наличные/карта, проценты/полосы; отрицательные компоненты или нулевой/отрицательный итог выключают доли целиком.
- AN05: На месте/С собой/Доставка из исходного snapshot. Отсутствующее поле — here; неизвестное значение — ошибка. Возврат использует способ исходной продажи; fee включён; количество новых чеков не уменьшается.
- AN06: категории (исторические, продажи DESC), товары (поиск, сумма/количество), сотрудники (автор продажи, чеки/средний чек). Все таблицы на одном экране; товарные суммы без delivery.
- AN07: строго «Товар | Израсходовано»; итог простых компонентов включая untracked, nested/yield/modifiers/direct и минус любой возврат по исходному составу. Совместимые исторические единицы объединяются по ID в кг/л/шт. Несовместимые единицы/цикл/нет metadata — ошибка, не ложный ноль. Fraction из RecipeCalculator сохраняется до общей суммы; отображение до 12 знаков HALF_EVEN только на итоговой границе.
- AN08: смены/склад/сверка и текущие движения доступны; Web-архив явно исключён.
- AN09: read-only, та же admin transaction и snapshot; без новых таблиц/миграций/зависимостей/сетевых эффектов. Продажи/реальный склад/возвраты не меняются.

Сортировка количеств группирует единицы: массу и литры нельзя осмысленно сравнивать одним числом. Исторические названия одного ID перечисляются через «/». Полный возврат — единственный поддерживаемый текущей кассой: частичные возвраты не добавлены.

## Таблицы — следующая визуальная правка 13.11.2026

Кнопки сортировки удалены. Категории и товары всегда сортируются по чистой выручке DESC, затем стабильному ID; используют единый SalesTable с акцентной шапкой (primary10%, радиус14) и одинаковым оформлением строк, отличающим их от остальных модулей. Расход — всегда net quantity DESC внутри единицы (кг/л/шт. не сравниваются между собой), ID разрешает равенство. Поиск/переключатели не возвращались.

Расход имеет compact-вариант таблицы: строго2столбца, вертикальные отступы7dp вместо13, промежуток2dp вместо6, bodySmall, без отдельных рамок у каждой строки, радиус8 вместо14; количество справа. Это визуальное уплотнение, не новая SQL-пагинация и не заявление об оптимизации загрузки большой базы.

13.11.2026 компоновка по просьбе владельца: после сводки слева сотрудники (более широкая колонка под таблицу), справа вертикально Оплата → Получение заказа. ## Поступления, расход и остаток — уточнение владельца

Только блок «Расход товаров и ингредиентов» теперь имеет4колонки: Товар / Поступило / Израсходовано / В наличии на ДД.ММ.ГГГГ. Ранее утверждённые2столбца и net расход в этой таблице заменены прямым решением владельца: расход показывает gross outgoing от продаж, без вычета возвратов (продано10кг, возвращено2кг → расход10кг). Сами исходные consumption/net DTO и остальные отчёты не переопределяются.

ConsumptionStockReports объединяет уже построенные consumption и warehouse из того же snapshot/транзакции:
- Поступило — фактически проведённые приёмки (invoiceQuantity) в выбранном периоде; черновики/ожидаемые поставки/внесения вручную не становятся поступлением.
- Израсходовано — simple-компоненты прямых продаж, рецептур и модификаторов, включая untracked; возвраты не вычитаются по новому правилу.
- В наличии — WarehouseRow.end на period.endExclusive (начало следующего дня), восстановленный по журналу, не WarehouseProduct.current. Возвраты, инвентаризация и ручные корректировки участвуют в фактическом остатке по своим движениям.
- Строки — объединение простых складских товаров и исторического расхода по ID; товар без продаж может показывать поступления/остаток и расход0. Исторические названия расхода сохраняются, для складских товаров без продаж используется имя из существующего warehouse report.
- Совместимые величины нормализуются точно в кг/л/шт. Несовместимые/неизвестные единицы, отсутствующая строка, неполный журнал, отключённый учёт остатка дают прочерк в недостоверной складской ячейке, не ложный ноль. Для untracked проведённая приёмка и расчётный расход остаются доступными.
- Сортировка gross consumed DESC внутри единицы, стабильный ID при равенстве. Компактный стиль сохранён.

Схема, posting и warehouse boundary policy не менялись; новых запросов к БД и побочных эффектов нет. Категории/товарная аналитика продаж не изменены.

Последняя правка владельца: колонка «В наличии» убрана из UI расхода. В таблице остаются Товар / Поступило / Израсходовано. Исторические остатки и их расчёт не удалены из моделей. Количества в кг во всех таблицах этой аналитики отображаются с2знаками после запятой (HALF_UP только при форматировании, например1.235→1,24кг). Остальные единицы отображаются как прежде; точные BigDecimal, агрегация и сортировка не изменены.
