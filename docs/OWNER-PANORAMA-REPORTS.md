# PDF владельцу: смена / месяц / квартал

Прямое поручение владельца13.11.2026: три независимых переключателя, получатель ownerChatId из Telegram, всегда один PDF. Оформление — текущая «Панорама»/AnalyticsPdf. Рабочая группа продолжает получать прежние сообщения/сменный чек, настройки темы/бота/получателя переиспользованы.

## План / acceptance

- OT01: в настройках отдельная секция Отчёты владельцу: Отчёт за смену, Отправлять отчёт за месяц, Отправлять отчёт за квартал. Флаги независимы, общий enabled и owner ID обязательны для отправки; group ID не заменяет owner ID, threadId сбрасывается для личного сообщения.
- OT02: SHIFT после каждого закрытия — только операции этой смены, без соседних смен того же дня; оригиналы возвратов нужны для проверки/исторических фактов, но не становятся новыми продажами. Внутренний доверенный read требует реальную сохранённую закрытую смену; не входит в сессию администратора и не пишет БД.
- OT03: MONTH —1число…последнее число месяца; QUARTER — календарные Jan–Mar/Apr–Jun/Jul–Sep/Oct–Dec. После каждого закрытия в последний день отправляется текущий итог до этого closedAt, как подтвердил владелец. Два закрытия — два обновлённых отчёта, разные close keys.
- OT04: если последний день был выходным и отправки не было, при первом следующем открытии смены (также при закрытии) отправляется пропущенный полный завершённый период. Пример30апреля выходной → открыть3мая → отчёт1–30апреля.31декабря выходной → открыть1января → декабрь +IVквартал. Применяется ко всем месяцам/кварталам, а не только январю.
- OT05: перезапуск/повтор события не дублирует отправку. Если отчёт последнего дня уже успешно ушёл и после его cutoff в периоде не было новых продаж/возвратов/приёмок, повтор не отправляется (final key=covered). Если появились — отправляется обновлённый окончательный итог. Покрытие восстанавливается из существующих sent close keys, отдельный необязательный marker не требуется. Невыясненный sending/unknown не обходится новым final key, retryAfter уважается.
- OT06: новое включение начинает планирование с текущего месяца/квартала, не рассылает произвольную старую историю до включения. Activation timestamp каждого флага сохраняется зашифрованно, не меняется при обычном редактировании, выключение сбрасывает только свой timestamp. При длительном перерыве проверяются завершённые периоды начиная с активации, уже sent/covered пропускаются.
- OT07: тот же historical SalesReport/ReportGroups/Consumption/ReportTrends/AnalyticsPdf, не новая денежная модель. Clock/cutoff фиксированы; итог последнего дня не захватывает более поздние операции того же дня. Поступления ограничены тем же time window; для SHIFT —openedAt…closedAt. PDF все строки раскрыты, gross profit как в UI; подписи смены с номером/временем/фамилией и инициалами, календарные с полными датами. PDF cache удаляется после подготовки вложения; реальные Telegram API не вызываются тестами.

## Реализация / совместимость

TelegramSettings дополнен ownerMonthReport/ownerQuarterReport +ownerMonthSince/ownerQuarterSince. Старые ownerMonthlyStats/monthlyWarehouse остаются retired=false и не активируют рассылку при восстановлении Web/старой копии. Codec version1 с optional новыми полями, старые файлы читаются как новые выключенные флаги; весь файл по-прежнему AES-GCM. Схема БД и кассовые posting не меняются.

SalesReportRepository публичный snapshot сохранил adminTransaction. Общий internal readSalesReport вызывается только из admin transaction или проверенного ownerPanorama/Room read transaction. SalesReports.build добавлены optional selected sale/refund IDs; валидация оригиналов неизменна, фильтр влияет только на выбранные события. Warehouse reader получил необязательные временные границы проведённых invoice facts; обычный UI вызов без window ведёт себя как прежде.

Периодические close/final keys включают dataset и digest(bot+ownerChat), не рабочую группу. Старые owner shift bundle/page journal markers учитываются, чтобы обновление не пересылало уже обработанную смену. TelegramDelivery сохраняет sending до I/O и sent после успеха; неизвестный результат сети автоматически не повторяется. Group failure не блокирует owner jobs; отправки владельцу сериализованы mutex. Смена рабочего dataset/restore blocking останавливает подготовку нового отчёта.

Срабатывание — событие успешного открытия/закрытия локальной смены. Это не серверный таймер: на выключенном планшете отправки нет, пропущенные периоды подхватываются при следующей смене. Если приложение закрылось после самого commit до вызова существующего callback, периодические отчёты подхватятся следующим событием; отдельная переработка durable outbox сменных callback в этот инкремент не входит.

## Проверки

OwnerReportScheduleTest: конец месяца/квартала, високосный февраль, любой выходной месяц, январь после декабря, независимые флаги/activation/legacy codec, coverage/unknown/retry, fake TelegramTransport +journal reopen, selected shift vsoriginal same-day receipt.

Room: существующие SalesReportRepositoryTest и OwnerAnalyticsIntegrationTest расширены/переиспользованы для read-only/cutoff/исторических имён; OwnerPanoramaHolidayTest — реальная продажа30декабря, нет смен31декабря, открытие1января, не-admin автоматический read, MONTH/Q4 границы, один PDF/подпись/все поля, таблицы до/после равны. TelegramPersistenceTest — encryption/reopen/activation state. AnalyticsPdfTest — регрессия базового PDF. UI переключатели и реальные сообщения принимает владелец вручную; тесты не отправляют ничего в Telegram.

Уточнение активации: отключение Telegram сбрасывает точку начала новых периодических отчётов. При повторном включении она устанавливается заново; периоды, когда отправка была отключена, автоматически не накапливаются. Обычное редактирование включённой конфигурации сохраняет точку начала.
