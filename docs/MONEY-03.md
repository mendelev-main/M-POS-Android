# Денежный контракт03 — решения и открытые примеры

Статус: базовая policy03b утверждена владельцем25.10.2026, pure SaleMoney ci-verified; runtime продажи ещё нет. BYN подтверждена ранее. Общие скидки/loyalty, partial refund и внешнее acquiring остаются отдельными контрактами.

## Утверждено

- Денежные вычисления BigDecimal, без Double. Оплачиваемые значения minor units Long, переполнение/некорректный ввод отклоняются.
- Округлять net сумму каждой строки до2знаков HALF_UP; итог товаров складывать из этих округлённых строк. Пример:0.05 BYN×3 со скидкой10%=0.135→0.14 BYN. Не округлять лишь общий итог и не округлять цену за единицу до умножения.
- Сначала поддержать полный возврат чека. Partial refund отложен и не изображается UI как доступный.
- Наличный возврат по вчерашней продаже сегодня создаёт связанную операцию выдачи сегодняшней смены, уменьшает сегодняшнюю кассу один раз. Продажа и её исходный shiftId остаются в истории; closed snapshot прошлой смены не переписывается. Отдельная ручная withdrawal того же refund запрещена.

Следствие line policy: три разные строки по0.05 со скидкой10% дают каждая0.045→0.05 и сумму0.15, тогда как одна строка qty3 даёт0.14. Объединение одинаковых конфигураций по W02 выполняется до окончательного расчёта. Отображение скидки должно сходиться с сохранёнными gross/net allocations; самостоятельное округление скидки с повторным вычитанием не должно менять утверждённые0.14. Конкретный gross/net allocation fixture закрепить перед реализацией скидок.

## Допуск к коду

Минимальная смена03a может хранить opening/counted/expected cash в minor units и transfer прошлого counted. При вводе BYN допускаются максимум2знака, отрицательный counted не принимается. Произвольные финансовые операции, ставка скидки, deposit/withdrawal UI не появляются только из-за наличия схемы смен.

Для дальнейших расширений отдельно закрыть order-level скидку/loyalty allocations и их сочетания, partial refund, внешний acquiring/reversal. Подтверждённый первый scope использует одну скидку строки, фиксированную скидку на единицу, отдельный delivery cash-out, cash change и remainder-first split — см. текущие D02 примеры ниже. Эквайринг отсутствует; запись «карта» не подтверждает внешний банковский платёж.

Fixtures для дальнейших тестов: утверждённые0.135→0.14;line-sum0.15 vs grouped0.14; полный исторический refund/replay/cross-shift−10 ровно один раз; остатки возвращаются по sale stock snapshot после изменения рецепта; fault не записывает половину refund. До реализации/CI это будущие тесты, не доказательство готовых оплат.

## D02 дополнено владельцем25.10.2026

Подтверждены новые примеры: чек100, cash40/card60, given50 →change10 и cash+40; equal split10/3 →3.34+3.33+3.33 (остаток первым частям); fixed discount1 за единицу при price10×qty2 →goods18, доставка5 отдельно →total23; одна скидка строки, loyalty в06. Доставка как в pinned Web сразу выдаётся наличными: goods20+fee5,total25/card25 при opening0 запрещён из-за отсутствия наличных, при opening5 допустим и cashAfter0. Cash25 при opening0 даёт cashAfter20. Refund первого scope — полный, cross-shift наличные относятся к смене выдачи, как подтверждено ранее.

Эти решения заменяют pending формулировки выше для перечисленных случаев. Общая order-level скидка и loyalty allocation не вводятся этим scope; будущие partial/external acquiring/reversal contracts по-прежнему отдельны. Нулевая часть при делении допускается как в Web (0.01/3→0.01+0+0), не вызывает внешнее списание.

Реализация утверждённой арифметики —SaleMoney, [CI55JVM](https://github.com/mendelev-main/M-POS-Android/actions/runs/40223239353); контракт инкрементов [SALE-03B](SALE-03B.md). Она ещё не связана с financial write/UI. Параметр available/opening cash в расчёте означает текущий ожидаемый наличный остаток перед новой продажей (включая предыдущие продажи/движения), не только float начала смены.
