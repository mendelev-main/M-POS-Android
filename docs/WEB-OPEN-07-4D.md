## 07.4d.1 — OP01–OP06

- OP01: current и parked дают отдельные read-only WebOpenOperation с source-file-scoped origin, source IDs/location/times, исходными line names/price/qty/basePrice/manualPrice/comments/modifiers и найденной в этой же копии discount definition. Повтор для идентичного файла детерминирован, source objects не меняются. Origin не является payment command ID; другой export даёт другой origin. Нет смешивания с target30 или локальными командами.
- OP02: проверочный total = сумма line net HALF_UP2 + delivery. Проценты рассчитываются точно, без промежуточного округления; fixed discount — за единицу с ограничением gross; percent ограничивается100 как Web. Две строки0.05×3−10% →0.14+0.14=0.28; source draft0.27 остаётся0.27, accepted0.10/unpaid0.17 не переписываются, появляется quoteTotalMismatch. Missing price/qty/discount →unknown total и blocker, не0 и не fallback из products.
- OP03: доставка добавляется только для исходного типа «Доставка», fee берётся из session; отсутствие подтверждения тарифа явно отмечается. Неизвестный тип не становится «На месте». Modifier delta уже включён в item.price, не начисляется ещё раз. Лояльность06 остаётся TODO, но положительный reward делает quote unavailable; accepted payments сохраняются. Нельзя убрать reward и повысить unpaid amount.
- OP04: единственная открытая source shift и её source actor — только кандидаты для дальнейшей сверки, не доказанный historical binding. Для paid session проверяются createdAt/payment updatedAt против openedAt; missing/предшествующая смене дата явно блокирует подтверждение. Source parked employeeName/timestamp сохраняются отдельно от candidate actor; автора отложенного не заменять сегодняшним кассиром. Для обычного unpaid parked не требовать, чтобы он был создан уже после открытия сегодняшней смены.
- OP05: payment facts07.4a сохраняют paid cash40/given50/change10/unpaid card60. All-paid draft требует сверки завершённого чека, не нового списания. Чек той же суммы в кандидатной смене — возможное пересечение, а не доказательство дубля; ни paid evidence, ни completed receipt не удаляются. Положительный webOrderId требует решения о completion отложенного09, его нельзя забыть из-за отсутствия сетевого UI.
- OP06: duplicate parked/line/modifier/discount IDs, malformed/negative/overflowing money, nonpositive quantities, invalid types/time/currency отказываются. Пустой unpaid current не создаёт операцию; пустой paid current сохраняет money evidence с blocker. Для qty точнее scale12 ставится reconciliation flag, без округления source quantities. Прямых Room/stock/cash/transport/print writes нет.

Все результаты сохраняют operationalCartMappingPending и cashHistoryReconciliationPending. Для paid есть sourceQuoteNotPersisted: совпадение расчёта с totalCents не доказывает, что каталожная рецептура/discount definition не менялась после приёма части. Нет readyToActivate/Charge API. DTO не заменяет полный исходный файл, который07.4e должен сохранить отдельно; тарифные/print/loyalty/online metadata нельзя молча потерять при последующей materialization.

## 07.4d.2a — CR01–CR06: сверка кассовых фактов

Статус: implemented, локальные269JVM/lint/debug/preflight и16Python tests passed; CI/device не заявляются. Это первая часть07.4d.2; native graph/cart mapping остаётся07.4d.2b.

- CR01: WebCashReconciliation возвращает source-file-scoped read-only сравнение каждой source shift. Отдельно openingCash, cash всех завершённых продаж (включая позже возвращённые), cash только active Web receipts, deposits/withdrawals/refund/delivery withdrawals. Ни одна исходная запись не удаляется и не проводится заново; повторное сравнение того же файла детерминированно. Missing allocations/opening остаются null, без подстановки0 или countedCash предыдущей смены.
- CR02: cashFromRecordedFacts = opening + gross completed cash + записанные deposits − записанные withdrawals. SourceDisplayedCash в точности повторяет pinned cashDrawerBalance: opening + nonreturned receipt cash + deposits − withdrawals + refund withdrawals. Разница сохраняется отдельно, без молчаливого выбора одного числа как рабочего остатка. Это арифметика записанных фактов, не доказанный физический пересчёт кассы.
- CR03: paid40/given50/change10 хранится как pendingCash40, не50; unpaid card60 не добавляется ни к кассе, ни к pendingCard. Уже принятые card parts показываются отдельно и не увеличивают наличность. Pending cash не включён в completed cash; includingPendingCash — только отдельный сравнительный итог. Связь со сменой проверяется как candidate из07.4d.1; старый/неизвестный timestamp, отсутствующий кассир/смена, unexpected parked paid, all-paid или возможное пересечение с completed receipt оставляют origin unassigned. Для открытой смены итог с неизвестно привязанной наличностью остаётся null, а не0/40/140 по догадке.
- CR04: для full refund cash allocation сверяется с source withdrawal по return shift/точному returnedAt/сумме и количеству. В pinned receipts.js один now записан и в receipt, и в withdrawal; отдельного receiptId в движении нет. Отсутствие/лишнее движение даёт mismatch; повторяющиеся одинаковые keys дают ambiguous даже при равных totals. Проверка не создаёт ещё одну выдачу денег. Card-only refund не требует кассового withdrawal. Незавершённые/неполные refund факты остаются gap.
- CR05: продажа10 во вчерашней смене и возврат10 в сегодняшней с opening20: recorded facts вчера+10, сегодня10; source UI может показать вчера0, сегодня20 из-за своей compensation formula. Разница явно блокирует автоматическое решение. Delivery25/courier5/refund25 при opening10 оставляет5 по записанным Web-движениям; нельзя изобрести исторический courier credit5 по новой native-политике. Courier withdrawals сверяются с total delivery всех source receipts, включая returned; несовпадение/неизвестная fee отмечается, реальные движения не выбрасываются.
- CR06: неизвестные shift refs, времена вне смены, orphan refund/delivery movements, повтор движения с тем же ID в разных сменах, negative recorded cash, saved expected cash mismatch отмечаются. Повторяющиеся записи не дедуплицируются по догадке. Другая объявленная currency и overflow Long отказываются до получения результата. Counted difference рассчитывается отдельно, исходный expected/count не переписывается.

WebCashComparison всегда содержит nativePaidProvenancePending; OP/shift blockers сохраняются. Модель не является opening command, native cash ledger или разрешением activate/charge. При наличии gaps числовые подытоги — диагностика, а не признанный кассовый баланс. Нельзя применять только одно поле includingPendingCash и игнорировать blockers/unassigned evidence. Полный source сохраняет07.4e; новые DTO не заменяют исходный файл.

Источник: pinned shifts.js/shiftTotals+cashDrawerBalance, receipts.js/processFullReturn, payment.js/completeSplitPayment+finalizePaymentSaved, android-safety.js acknowledged current-session storage. Source regression source-product-stock.test.cjs: same-shift cash/card/mixed return drawer balance и journaled split progress. Междусменная разница — следствие прочитанной source formula, покрываемое отдельным Kotlin fixture, а не утверждение, что старый тест её проверял.
