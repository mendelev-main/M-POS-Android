Статус: planned кроме обновления APK 00.1. Источник сайта — pinned Web `web-orders.js`, `availability.js`, `android-integrations.js`/`android-bridge.js`; контракты backend отдельно проверяются перед 09.

Сохранить настройки и «Проверить подключение» — разные действия. Отказ записи запрещает проверку с несохранённым конфигом и сообщение «Сохранено». Не очищать другие группы при сохранении одной формы. Изменение критического конфига запрещено во время несовместимой операции; revision предотвращает overwrite открытой устаревшей формой.

## Локальные и сетевые настройки

Секрет устройства хранится через платформенный защищённый adapter, masked в UI; logs/backup/release assets его не содержат. URL принимается после parse/проверки HTTPS, без embedded credentials; тестовые локальные исключения только в явном debug/staging режиме. Смена backend/device binding требует подтверждения и отдельной судьбы незавершённых outbox: записи прежнего магазина не отправляются автоматически в новый.

Runtime admin session не хранится как preference. Изменения ролей проверяются внутри команды. Будущая секретная конфигурация никак не меняет публичный APK update endpoint и постоянный signing identity.

## Наблюдаемый Web transport, не окончательный backend контракт

В pinned `web-orders.js` видны `GET /api/orders/events` (SSE), `POST /api/orders/{id}/accept` с readyEstimate и `POST /api/orders/{id}/ready`; mutation запросы используют `X-Device-Key`. Исходный EventSource передаёт deviceKey в query. Для native предпочтителен header auth, но поддержка header на SSE должна быть проверена backend до изменения транспорта. Не объявлять замену query совместимой без теста; секреты в URL не логируются.

Наблюдаемые пути не доказывают полный schema, статусные переходы, server idempotency или replay retention. До 09 собрать обезличенные request/response/event fixtures, ошибки 401/403/409/429/5xx, timeouts и reconnect. Никаких production test orders ради разработки.

## Заказы сайта — N01/N02/N03/N05

Список показывает serverOrderId, время, тип, состав, сумму и статус синхронизации. Приём заказа: durable локальная операция с ключом serverOrderId/action → запрос → подтверждённое состояние; неопределённый ответ остаётся pending и сверяется, не создавая второй заказ. Отдельно различаются «принят», «готов», «оплачен»: готовность не является receipt оплаты. Конкретный state machine фиксируется по backend.

N01: offline/HTTP/abort/error показываются с последним подтверждённым состоянием; 401 требует исправления привязки, а не бесконечных успешных retry. N02: SSE reconnect с backoff/jitter, обработка id/retry по поддержанному сервером контракту; без replay проводится reconciliation списка. Не обещать exactly-once delivery от SSE. N03: уникальная локальная привязка serverOrderId защищает от replay/двух потоков/рестарта, переход повторяемый. N05: каталог/черновики/локальная касса работают независимо от SSE и очереди.

## Меню, фото, доступность и тарифы — N04/N06

Два флага — видимость в online меню и доступность online заказа — сохраняются отдельно на товаре/категории. Локальный POS не скрывает товар только из-за online-флага. До sync определить precedence товар/категория, сопоставление ID, ownership каждого поля и удаление удалённых объектов.

Ручная синхронизация показывает preview/объём, прогресс по меню/фото и итог частичного успеха. Фото не объявляется опубликованным до подтверждения upload. Retry отправляет только незавершённые версии; сохранённые локальные данные не откатываются из-за сети. Availability рассчитывается из тех же точных единиц/рецептов, но серверная публикация и частота имеют отдельный контракт; allowNegativeStock не делает online запас бесконечным.

Тариф доставки — выбранный объект/версия и snapshot суммы в заказе. Переключение на «С собой» исключает доставку из итога, изменение справочника не меняет оплаченный receipt. Условия тарифов/зон и округление сверяются с `tests/delivery-tariffs.test.cjs` и backend до кода.

N06: контрактные tests с fake HTTP/SSE, restart pending actions, schema drift и staging walkthrough обязательны до подключения реального магазина. Backend deployment/изменение сайта в этот этап автоматически не входит.
