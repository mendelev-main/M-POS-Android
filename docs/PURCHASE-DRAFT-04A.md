# 04a.2 — черновик закупки

Статус: implemented, проверки API36 pending. Это часть M11/I01/I04, весь склад не завершён.

## Источник и границы

Pinned Web1682c883: `Web/js/features/purchase-orders.js`, `android-purchase-validation.js`, `product-configuration.js`. Нативный экран открывается вкладкой «Заказы поставщикам». Показываются только закреплённые простые товары выбранного поставщика; пустая привязка не заменяется всеми товарами каталога. Поставщика нельзя менять при наличии строк. Используются общие Mpos theme/field/select/button/dialog, без нового локального дизайн-стандарта.

Здесь реализованы выбор, редактирование и явное сохранение одного черновика на установку. «Сформировать заказ» и «История» пока показывают «Скоро будет подключено». Pending order, приёмка, стоимость, расходы и сторно — следующие части. Сохранение не проводит закупку, не меняет остатки, себестоимость, движения и настройки упаковок товара.

В Web новый черновик живёт в RAM. Durable native draft — осознанное расширение. Гарантия восстановления после холодного запуска относится к нажатию «Сохранить черновик»; несохранённый ввод сохраняется при recreation через ViewModel, автоматическое сохранение после process kill не обещается. Уход/перечитывание грязной формы требуют общего подтверждения, которое не удаляет сохранённую версию.

## Контракт строки

Строка сохраняет productId/revision/name/baseUnit и исходные текстовые quantity/orderUnit/packSize/contentUnit. Поставщик сохраняет id/revision/name. Quantity допускает пустое значение и ноль для незавершённой строки; это не готовая положительная позиция будущего заказа. Отрицательные, NaN, exponent, несовместимые единицы, нулевая заданная упаковка и превышение decimal precision отклоняются.

Примеры: 24 бутылки ×500мл =12л; 2 коробки ×6000мл =12л; 0,4г =0,0004кг. Только BigDecimal и совместимые physical dimensions, без Double и округления до 0,001. Максимум12 дробных/18 целых знаков, переполнение отклоняется. Неизвестная packSize остаётся пустой, expectedQty=null; она не подменяется нулём или единицей. Вложенный множитель «2 коробки ×12 бутылок ×0,5л» в source UI отсутствует: использовать эквивалентные 24 бутылки ×500мл или 2 коробки ×6000мл, без выдуманного трёхфакторного контракта.

Catalog packSize уже нормализована в базовой единице (CATALOG-01B). Начальная строка использует её с contentUnit=baseUnit. Пользовательский ввод500мл сохраняется именно как500мл; при повторном открытии он не пересчитывается заново из изменённых defaults каталога.

## Хранение, конфликты и отказы

Room schema8 без SQL migration: `workspace_documents`, namespace `purchase-draft`, payload version1, nullable draft. Это постоянные бизнес-данные для будущего backup, не очищаемый cache. Неизвестный/повреждённый payload блокирует чтение/запись; автоматического сброса нет.

Save/Clear проверяют локального owner в repository и InstallationGate. Это не заменяет будущие роли/сессии05. Одна Room transaction записывает document revision, fingerprinted operation result и audit event. CAS по document revision защищает двух редакторов. Параметры команды фиксируются перед ожиданием gate. Повтор commandId с тем же fingerprint возвращает исходный результат до проверки устаревших ссылок; другой payload с этим ID отклоняется. Повтор старого Save после Clear не восстанавливает удалённый черновик.

Save проверяет текущие supplier/product revisions, имя, базовую единицу, существование и привязку простого товара. Stale draft читается без потери исторических полей. «Обновить ссылки» явно обновляет revision/name, сохраняет quantities/pack fields; несовместимая baseUnit/отвязанный товар требуют исправления строк. Новая версия самого draft не усваивается этим действием: сначала нужно явно перечитать, подтвердив потерю несохранённого ввода.

Удаление выбранного поставщика/товара блокируется внутри той же транзакционной границы, включая product guard после снятия supplier binding. Rename/unlink разрешены, но делают сохранённые ссылки stale. Clear позволяет удалить stale draft без подмены его ссылок.

При неизвестном результате блокируются новые изменения; «Проверить результат» использует ту же команду. Известный commit с ошибкой последующего чтения остаётся известным сохранением, повторная запись не требуется. Отказ SQLite на любой из трёх записей откатывает всё, без ложного UI успеха.
