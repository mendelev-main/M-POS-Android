# Этапная работа M-POS

Прочитайте `AGENTS.md`, `PLANS.md` и файл этапа `harness/build/NN-*.md`. Установите зависимости и точные acceptance IDs. Прочитайте существующий context и результаты в `harness/build-log.md`; не считать старый planned статус evidence.

До реализации сверьте предметный сценарий с pinned Web revision из `config/reference.json`: найдите feature, Android adapter и регрессионный тест. Читайте только нужные файлы. Если исходник/документ расходятся, запишите обнаруженное поведение и выбранное решение в context. Обновление reference commit — явное изменение требований, а не автоматический fetch HEAD.

Разбейте текущий этап на обозримые изменения, каждое с наблюдаемым результатом. Создайте context при начале этапа. Сначала реализуйте вертикальный сценарий с хранением и тестами, затем остальной UI. Не начинайте следующий этап без задачи на него. Обычные исправления внутри поставленной задачи не требуют нового согласования.

После изменений выбирайте минимальные необходимые локальные проверки по AGENTS.md: preflight для harness/контрактов, компиляция и адресные тесты для затронутого Kotlin-сценария. Не запускайте полный harness android/весь connected suite на каждую визуальную правку. При отсутствии среды записать blocker и оставить проверки pending. Владелец проверяет работу в Android Studio и сверяет интерфейс с Web; фиксируйте его подтверждение отдельно от тестов.

Обновите parity для точных IDs. В журнале укажите commit, команды/Actions URL, наблюдаемый результат и незакрытые device cases. В context хранить решения/ограничения, а не полный транскрипт и не секреты. Завершение этапа требует его acceptance, частичное выполнение так и назвать.

С2026-11-07 рабочая ветка main, новые изменения в develop запрещены решением владельца. Каждый commit/push main запускает полный release pipeline, включая docs-only. Итоговые evidence можно приложить отдельным отчётом в outputs без создания рекурсивных коммитов ради записи результата каждого такого docs pipeline.

Последнее уточнение владельца2026-11-07: сначала локальная реализация и проверки, затем утверждение конкретного набора изменений, затем push remote/main. Не отправлять каждый локальный инкремент и не запускать удалённый release workflow до утверждения. Приоритет у этой последовательности; DAG каждого согласованного push сохраняется.

Последнее правило: агент ведёт код, содержательные тесты, документацию и harness; UI и готовность принимает владелец в Android Studio. Push только по прямой команде владельца, не по общему одобрению дизайна и не по разрешению на прошлый пакет.

Действующее решение владельца2026-11-11: UI acceptance ручная, автоматические Compose/UI tests и UI-driven debug update/recovery E2E убраны из CI. Не добавлять новые UI-тесты и не восстанавливать эти gates без команды владельца. Автоматические JVM/lint/Room/данные/signature/package/process/UID/private-marker checks сохраняются. Все упоминания старого full UI suite выше описывают прежний workflow, а не текущую обязательную проверку.
